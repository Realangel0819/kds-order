## 1. 1주차 한 줄 정의

> *"스프링의 뼈대(IoC/DI)와 영속성(JPA)을 이해하고, 모놀리식의 한계를 겪은 뒤 멀티모듈과 gRPC를 통해 **'서비스 간 경계와 통신의 최적화'*_를 눈으로 증명한 주차."_

## 2. 단계별 기술 진화 과정 및 핵심 깨달음

### 🌱 Phase 1. 기본기 다지기 : 스프링의 제어권과 JPA의 마법 (Day 1 ~ Day 2)

- **IoC와 DI의 본질:** 객체의 생성과 생명주기를 개발자가 직접 관리하는 것이 아니라 스프링 컨테이너(IoC)가 주도하며, `Reflection API`를 통해 빈을 싱글톤으로 생성해 주입(DI)한다는 것을 이해했습니다.
    
- **생성자 주입(`@RequiredArgsConstructor` + `final`)의 이유:** 단순히 코드가 깔끔해서가 아니라, 객체의 불변성(Immutability)을 보장하여 런타임에 의존성이 교체되는 리스크를 원천 차단하고, 스프링 없이도 순수 자바 코드로 **단위 테스트**를 작성하기 위함임을 깨달았습니다.
    
- **JPA 영속성 컨텍스트와 Dirty Checking:**
    
    - 자바 객체의 값을 바꾼다고 해서 바로 DB에 반영되는 것이 아님을 배웠습니다. `@Transactional`이 커밋되거나 `flush()`가 호출되는 시점에 1차 캐시의 스냅샷과 현재 상태를 비교(Dirty Checking)해야만 비로소 `UPDATE` SQL이 나간다는 메커니즘을 명확히 이해했습니다.
        

### 🏗️ Phase 2. 모놀리식의 한계와 멀티모듈 구조 분리 (Day 3 ~ Day 4)

- **왜 서비스를 나누어야 하는가?**
    
    - 단일 구조에서는 특정 도메인에 트래픽이 몰릴 때 전체 시스템이 마비되는 장애 전파(Cascading Failure)와 확장성의 한계가 명확합니다. 따라서 도메인 경계(Domain Boundary)에 따라 `Order Service`와 `Menu Service`의 책임을 엄격하게 분리해야 합니다.
        
    - 컨트롤러가 레포지토리를 직접 호출하면 관심사의 분리(SoC) 원칙이 깨지고 변경에 취약해지므로, 반드시 Service를 거쳐야 함을 체득했습니다.
        
- **패키지 분리 vs 멀티모듈 분리:**
    
    - 단순히 패키지만 나누는 것은 컴파일 시점의 격리를 강제하지 못해 아키텍처가 쉽게 오염됩니다. 반면, Gradle 멀티모듈은 `build.gradle`에 의존성을 명시하지 않으면 `import` 자체가 불가능하므로 **물리적인 의존성 격리**를 강제할 수 있는 강력한 도구임을 배웠습니다. (단, 공통 모듈에 무작정 코드를 넣는 **God Module 안티패턴**과 순환 참조는 항상 경계해야 함을 인지했습니다.)
        

### ⚡ Phase 3. 고성능 내부 통신과 방어벽 구축 : gRPC (Day 5 ~ Day 6)

- **REST vs gRPC:**
    
    - 내부 마이크로서비스 간 통신에서 텍스트 기반의 JSON과 HTTP/1.1은 불필요한 오버헤드와 Head-of-Line Blocking 문제를 유발합니다.
        
    - 반면 gRPC는 **Protocol Buffers**를 통한 바이너리 직렬화로 페이로드 크기를 획기적으로 줄이고, **HTTP/2 Multiplexing**을 통해 하나의 TCP 커넥션으로 수많은 요청을 동시에 처리하여 내부 통신 지연을 극복합니다.
        
- **장애 방어벽 (Timeout & Retry):**
    
    - MSA 환경에서 네트워크는 언제나 실패할 수 있습니다. `Menu Service`가 멈췄을 때 `Order Service`가 무한정 응답을 기다리면 톰캣 스레드가 고갈되는 **Thread Pool Starvation**이 발생합니다.
        
    - 이를 막기 위해 gRPC Deadline(타임아웃)을 걸어 스레드를 선제적으로 해제하고, 일시적 장애 대응을 위해 지수 백오프(Exponential Backoff)를 적용해야 함을 배웠습니다.
        

## 3. 1주차 주요 트러블슈팅 및 해결 기록

1. **JPA 변경 감지 누락 이슈:**
    
    - _원인:_ `@Transactional`이 누락된 서비스 메서드에서 엔티티 값을 변경했으나 DB에 반영되지 않음.
        
    - _해결:_ 변경 감지와 쓰기 지연은 트랜잭션 커밋 시점에 동작하므로, 비즈니스 로직 전반에 명확한 트랜잭션 경계가 설정되어야 함을 확인.
        
2. **H2 콘솔 접속 경로 불일치:**
    
    - _원인:_ `application.yml`의 파일 경로 설정과 웹 브라우저의 접속 URL 파라미터가 달라서 발생.
        
    - _해결:_ JDBC URL 설정을 코드와 정확히 일치시켜 해결.
        
3. **Gradle 멀티모듈 의존성 설정:**
    
    - _원인:_ 모듈 간 참조 관계를 `settings.gradle`과 개별 `build.gradle`에 명확히 선언하지 않아 컴파일 에러 발생.
        
    - _해결:_ 루트 `settings.gradle`에 모듈 등록 및 각 서비스 모듈의 `implementation project(':common')` 선언 규칙 확립.
        

## 4. 면접관에게 자신 있게 꺼낼 수 있는 1주차 핵심 Q&A

- **Q. 생성자 주입(`@RequiredArgsConstructor`)을 고집하는 이유는 무엇인가요?**
    
    - `final` 키워드를 통해 객체의 불변성을 보장하고, 런타임에 의존성이 누락되거나 변경되는 사고를 원천 차단합니다. 또한 스프링 컨테이너 실행 없이 순수 자바 객체만으로 단위 테스트를 작성하기 매우 유리하기 때문입니다.
        
- **Q. 영속성 컨텍스트의 1차 캐시와 변경 감지는 어떻게 동작하나요?**
    
    - 트랜잭션 내에서 조회된 엔티티는 1차 캐시에 저장되어 DB 조회 비용을 줄이고 동일성을 보장합니다. 변경 감지는 최초 조회 시점의 스냅샷과 트랜잭션 커밋 시점의 상태를 비교하여 변경 사항을 자동으로 감지하고 쓰기 지연 SQL 저장소에 반영하는 구조입니다.
        
- **Q. 내부 서비스 간 통신에 REST 대신 gRPC를 선택한 이유는 무엇인가요?**
    
    - 텍스트 기반 JSON과 HTTP/1.1은 내부 통신에서 직렬화 비용과 네트워크 대역폭 낭비가 큽니다. gRPC는 바이너리 기반의 Protocol Buffers와 HTTP/2 멀티플렉싱을 활용하여 대규모 내부 트래픽 처리에서 성능과 안정성이 훨씬 뛰어나기 때문입니다.
