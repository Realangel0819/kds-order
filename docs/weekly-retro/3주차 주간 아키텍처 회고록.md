# 3주차 주간 회고: 스트리밍, 대용량 통계 배치, 그리고 검색 최적화

## 1. 3주차 한 줄 정의

> **"단순 DB 저장을 넘어, 조리 효율을 높이는 배치 알고리즘을 구현하고, 그 결과를 논블로킹(WebFlux)으로 주방에 실시간 스트리밍하며, 방대한 데이터를 Spring Batch와 Elasticsearch로 안전하게 통계·검색해 낸 '아키텍처 고도화'의 주간"**

## 2. 단계별 기술 진화 과정 및 핵심 깨달음

**① 비즈니스 병목 해결 알고리즘 (Batch Grouping)**

- **진화:** 주문이 들어오는 족족 주방에 전달하던 방식을 버리고, 30초/1분 등 특정 시간(Window) 동안 같은 메뉴를 바구니에 담아 묶음 처리(Grouping)하도록 개선했습니다.
    
- **깨달음:** 응답 지연 시간(Latency)을 살짝 희생하더라도, 주방의 전체 조리 처리량(Throughput)을 극대화하는 것이 실제 비즈니스에 더 큰 가치를 창출한다는 Trade-off를 배웠습니다.
    

**② 비동기 논블로킹 스트리밍 (WebFlux & SSE)**

- **진화:** 전국 매장의 KDS(주방 모니터)가 지속적인 연결을 유지해야 하는 상황에서, 스레드를 점유하는 Spring MVC 대신 Event Loop 기반의 WebFlux(Netty)와 SSE(Server-Sent Events)를 도입했습니다.
    
- **깨달음:** 무거운 WebSocket 대신 가벼운 단방향 HTTP 스트리밍(SSE)을 선택하는 기술적 안목과, 소수의 스레드로 C10K 문제를 해결하는 논블로킹 패러다임의 강력함을 체감했습니다.
    

**③ 대용량 데이터 안전 적재 (Spring Batch)**

- **진화:** 일일 조리 통계를 집계할 때 메모리 폭발(OOM)을 막기 위해 100건씩 쪼개어 처리하는 Chunk 지향 처리 배치를 도입했습니다.
    
- **깨달음:** 대용량 처리에서는 '빠른 것'보다 '실패했을 때 어디서부터 복구할 것인가(JobRepository)'와 '통계 갱신 중 화면이 텅 비지 않게 하는 법(PENDING-ACTIVE Swap 멱등성)'이 핵심임을 배웠습니다.
    

**④ 점진적 마이그레이션 (Kotlin & Kotest)**

- **진화:** 실시간 알림 파이프라인(Notification)을 순수 Kotlin 모듈로 분리하고 Kotest 기반 BDD 테스트를 도입했습니다.
    
- **깨달음:** 컴파일 타임에 `null`을 방어하는 Null Safety의 안정성과, AOP 프록시 충돌을 막는 `kotlin-spring` 플러그인의 원리를 이해하며 언어의 동작 방식을 더 깊이 이해했습니다.
    

## 3. 3주차 주요 트러블슈팅 및 해결 기록

**🚨 Trouble 1. Sinks.Many 멀티캐스트 동시성 에러**

- **증상:** 다중 스레드(Kafka 리스너와 수동 API)가 WebFlux의 `sink.tryEmitNext()`를 동시에 호출할 때 `FAIL_NON_SERIALIZED` 에러가 나며 알림이 유실됨.
    
- **해결:** 처음엔 `@Synchronized` 락으로 풀려 했으나 이벤트 루프를 블로킹(Blocking) 시키면 안 된다는 WebFlux의 철학에 맞춰, `Sinks.EmitFailureHandler.busyLooping(100ms)`을 도입하여 논블로킹 방식의 재시도(Retry) 로직으로 우아하게 해결함.
    

**🚨 Trouble 2. SSE 구독자 0명 시 파이프라인 영구 종료 현상**

- **증상:** 밤 10시에 영업이 종료되어 모든 KDS가 접속을 끊으면(구독자 0명), 다음 날 아침 다시 접속해도 알림이 전혀 오지 않음.
    
- **해결:** WebFlux Sinks의 기본값이 `autoCancel=true`로 되어 있어, 마지막 구독자가 떠나면 파이프를 폭파(Complete)시킨다는 내부 원리를 파악. 파이프 생성 시 `autoCancel=false` 옵션을 주어 서버 재시작 없이도 영구적으로 이벤트를 대기하도록 방어함.
    

**🚨 Trouble 3. ES 데이터 정합성 보장과 DLQ 설계**

- **증상:** MySQL 에는 저장되었으나 일시적인 네트워크 장애로 Elasticsearch 동기화(Kafka Consume)에 실패할 경우 데이터 불일치 발생.
    
- **해결:** Kafka Consumer에 지수 백오프(Exponential Backoff) 재시도를 적용하고, 최종 실패 시 DLT(Dead Letter Topic)로 격리. 나아가 매일 새벽 3시 30분에 도는 `OrderReindexJob` 배치를 통해 MySQL을 기준으로 ES에 누락된 데이터를 강제 덮어쓰기하여 최종적 일관성(Eventual Consistency)을 완벽히 보장함.
    

## 4. 면접관에게 자신 있게 꺼낼 수 있는 3주차 핵심 Q&A

**Q1. 실시간 주방 알림(KDS)을 구현할 때, 왜 Spring MVC(Tomcat)를 쓰지 않고 Spring WebFlux(Netty)를 도입했나요?**

> "KDS는 주문이 들어올 때까지 실시간으로 대기해야 하므로 HTTP 커넥션을 아주 길게 유지(Long-Polling 또는 SSE)해야 합니다. 이를 Tomcat 환경에서 구축하면 1개의 커넥션이 1개의 스레드를 계속 묶어두게(Blocking) 되어, 매장 수가 늘어나면 스레드 풀이 고갈되는 'Thread Starvation'으로 서버가 뻗습니다. 반면 WebFlux는 이벤트 루프 기반의 논블로킹 I/O를 사용하여, 소수의 스레드(보통 코어 수 x 2)만으로도 수만 개의 유휴 커넥션을 메모리 낭비 없이 쥐고 있을 수 있어 선택했습니다."

**Q2. 일일 통계를 낼 때, 단순히 비동기 스레드나 `@Scheduled` + `for문`을 돌리지 않고 왜 무거운 Spring Batch를 사용했나요?**

> "10만 건의 주문을 일반 for문으로 돌리면 서버 메모리가 터집니다(OOM). Spring Batch는 `JpaPagingItemReader`를 통해 데이터를 100건(Chunk)씩만 메모리에 올려 트랜잭션을 잘게 쪼개어 OOM을 방지합니다. 더 중요한 것은 **내결함성과 상태 관리**입니다. 일반 for문은 5만 번째에서 에러가 나면 어디까지 했는지 알 수 없지만, Batch는 메타 테이블에 상태를 기록해 실패한 지점부터 정확히 재시작할 수 있기 때문입니다."

**Q3. ES에 데이터를 동기화하다 실패할 경우를 대비해 새벽에 '재색인 배치'를 도는 방식을 택하셨는데, 이때 정합성은 어떻게 보장되나요?**

> "이 시스템의 Single Source of Truth(단일 진실 공급원)는 MySQL입니다. 재색인 배치는 어제 'COMPLETED' 처리된 주문 데이터를 MySQL에서 500건씩 끊어 읽어 그대로 ES로 덮어씁니다. ES의 Document ID를 MySQL의 PK와 동일하게 맞췄기 때문에, 설사 이미 ES에 일부 데이터가 들어가 있다 하더라도 업데이트(Upsert)로 덮어씌워지므로 완벽한 멱등성이 보장되고 최종적 일관성을 확보할 수 있습니다."
