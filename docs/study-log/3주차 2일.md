## 배운 개념 (내 언어로 설명)

C10K 문제는 ==**단일 서버가 1만 명 이상의 클라이언트와 동시에 네트워크 연결을 유지하고 처리할 때 성능이 급격히 떨어지는 현상**==

해결법 : Reactive Programming과 WebFlux
스레드를 멈춰 세우지 않고(Non-blocking), 일이 끝나면 콜백(이벤트)으로 알려줘서 소수의 스레드만으로 수만 개의 연결을 처리하는 패러다임

- **Reactive Programming:** 데이터 스트림과 상태 변화의 전파를 중심으로 하는 비동기 프로그래밍 패러다임. (Backpressure 지원)
    
- **Spring WebFlux:** Spring 5.0부터 도입된 Reactive 웹 프레임워크로, 기본 내장 서버로 비동기 이벤트 기반의 **Netty**를 사용합니다.


WebFlux(Netty)는 Thread-per-request 방식을 버리고 **Event Loop (이벤트 루프)** 모델을 사용합니다.

1. 요청이 들어오면, 소수의 Thread(보통 CPU 코어 수 x 2)로 구성된 Event Loop가 요청을 받습니다.
    
2. Event Loop는 이 요청을 처리하다가 I/O 작업(DB 조회, 네트워크 통신 등 대기 시간이 필요한 작업)을 만나면, **그 자리에 멈춰서 기다리지 않습니다(Non-blocking).**
    
3. 작업을 백그라운드로 던져놓고, Event Loop Thread는 즉시 다음 요청을 받으러 갑니다.
    
4. 백그라운드 작업이 끝나면 **"나 끝났어!"** 하고 이벤트를 발생시키고, Event Loop가 다시 이어서 결과를 클라이언트에게 응답합니다.

  개발자가 WebFlux 코드 내부에 일반 `RestTemplate`(동기식)이나 일반 `JPA`(JDBC는 기본적으로 블로킹)를 써버리면 어떻게 될까요? 단 4~8개의 스레드가 멈춰(Blocking) 버리기 때문에, **수천 개의 모든 요청이 올스톱되는 대형 장애**가 발생합니다. (이른바 Thread Starvation).


만약 내일 KDS 실시간 알림을 WebFlux가 아니라 Spring MVC로 구현한다면, 트래픽이 몰리는 피크타임 때 우리 백엔드 시스템(톰캣)의 스레드 풀과 메모리에서는 구체적으로 어떤 물리적인 문제가 발생하게 될까요?
- **스레드 풀 고갈 (Thread Starvation):** Tomcat의 기본 스레드 풀은 200개입니다. 만약 전국 500개 매장의 KDS가 실시간 알림을 받기 위해 연결을 맺고 대기한다면? 200개의 스레드가 몽땅 '대기' 상태로 묶여버립니다. 201번째 주문이 들어오면 서버는 스레드가 없어 응답을 못 하고 그대로 뻗어버립니다.
    
- **메모리 터짐 (OOM)과 컨텍스트 스위칭:** 스레드를 강제로 1만 개로 늘리면 안 되냐고요? Java에서 스레드 1개는 약 1MB의 메모리를 먹습니다. 1만 개의 연결을 유지하려면 아무것도 안 해도 메모리만 10GB가 날아갑니다. 게다가 OS가 1만 개의 스레드를 번갈아 실행(Context Switching)하느라 CPU가 폭주하게 됩니다.


## 3주차 2일차 핵심 면접 질문과 모범 답변 정리입니다.

1. **Spring MVC와 Spring WebFlux의 내부 동작 방식 차이를 설명해 주세요.**
    
    - MVC는 스레드 풀에서 스레드를 꺼내 하나의 요청을 끝날 때까지 대기(Blocking)하는 'Thread-per-request' 모델입니다.
        
    - WebFlux는 비동기/논블로킹 기반으로, 소수의 스레드가 이벤트 루프(Event Loop)를 돌며 처리합니다. 연결이 수만 개여도 대기 상태로 스레드를 붙잡지 않아 자원 낭비가 적습니다. 단, 코드 내 한 곳이라도 블로킹이 발생하면 적은 수의 스레드가 멈춰버려 전체 시스템 장애(Thread Starvation)가 올 수 있습니다.
        
2. **실시간 통신을 위해 WebSocket 대신 SSE(Server-Sent Events)를 선택한 이유는 무엇인가요?**
    
    - KDS(주방 모니터)는 서버로 데이터를 보낼 일이 없고, 주문 알림을 받기만 하면 됩니다.
        
    - WebSocket은 양방향 통신이라 무겁고 오버스펙입니다. 반면 SSE는 HTTP 기반의 단방향 통신이면서 서버와 지속적인 연결(Connection)을 유지하며 데이터를 푸시할 수 있어, 현재 요구사항에 가장 가볍고 정확하게 부합합니다.
        
3. **WebFlux를 사용할 때 절대 일반 JDBC나 RestTemplate을 함께 쓰면 안 되는 이유는 무엇인가요?**
    
    - WebFlux는 매우 적은 수(보통 4~8개)의 워커 스레드가 이벤트 루프를 통해 수많은 요청을 논블로킹으로 번갈아 가며 처리합니다.
        
    - 이때 동기/블로킹 방식인 일반 JDBC나 RestTemplate을 쓰면, 스레드가 응답을 기다리며 멈춰버립니다(Blocking). 결국 일할 스레드가 남아나지 않게 되는 스레드 고갈(Thread Starvation)이 발생해, 시스템 내의 모든 요청이 올스톱되는 치명적인 대형 장애로 이어집니다.
        
4. **Blocking과 Non-Blocking의 차이를 '제어권' 관점에서 설명해 주세요.**
    
    - 작업을 호출했을 때 **제어권**을 언제 돌려주느냐의 차이입니다.
        
    - **Blocking**은 작업이 끝날 때까지 제어권을 안 주고 호출한 스레드를 계속 대기(Wait) 상태로 묶어둡니다.
        
    - **Non-blocking**은 작업 완료 여부와 상관없이 즉시 제어권을 돌려주어, 호출한 스레드가 대기하지 않고 다른 일을 계속할 수 있게 합니다.
        
5. **`@GetMapping(produces = MediaType.TEXT_EVENT_STREAM_VALUE)`의 역할은 무엇인가요?**
    
    - HTTP 응답 헤더의 `Content-Type`을 `text/event-stream`으로 지정해 줍니다.
        
    - 이 헤더를 받은 클라이언트(브라우저)는 "한 번 응답을 받고 끝나는 것이 아니라, 서버가 연결을 끊지 않고 스트림 형태로 데이터를 계속 밀어주겠구나"라고 인식하고 지속적으로 대기하게 됩니다.
