## 오늘 목표

- **오늘 무엇을 이해해야 하는가?** RDBMS(MySQL)의 검색/집계 한계와 Elasticsearch의 동작 원리(역인덱스).
    
- **왜 배우는가?** 트랜잭션 처리가 핵심인 메인 DB(MySQL)에 무거운 통계/검색 쿼리를 날리면 시스템 전체에 장애를 유발할 수 있기 때문입니다.
    
- **프로젝트의 어디에 사용되는가?** 어제 만든 Spring Batch로 집계한 일일 통계 데이터나, 방대한 주문 이력을 빠르고 유연하게 검색하는 API에 사용합니다.
    
- **설명할 수 있어야 하는 것:** MySQL의 `LIKE` 검색과 ES의 `Inverted Index(역인덱스)`의 차이, 그리고 MySQL 데이터를 ES로 언제/어떻게 동기화할 것인가(정합성 문제).

  

## 배운 개념 (내 언어로 설명)

- Elastic search 는 텍스트 검색과 통계분석에 특화된 검색엔진(데이터베이스)
- Apache Lucene 기반으로 오픈소스 분산형 RESTful 검색엔진 및 분석엔진 JSON형태로 저장
- 쓰기/트랜잭션에 강한 DB(MySQL)와 읽기/검색에 강한 DB(Elasticsearch)를 분리하여 역할을 나눕니다
- - **일반 DB (Forward Index):** 문서 ID가 주어지면 내용을 찾습니다. (예: 1번 책 -> 내용 주르륵)
- **역인덱스:** 책 맨 뒤의 '찾아보기(색인)' 페이지와 같습니다.
    
    - "치킨" -> 문서 1번, 4번, 10번
    - "피자" -> 문서 2번, 4번
- 데이터가 들어올 때 ES 내부의 Analyzer(분석기)가 문장을 형태소 단위로 다 쪼개서(예: "양념 치킨 세트" -> "양념", "치킨", "세트") 이 역인덱스 사전을 미리 만들어 둡니다. 그래서 검색 시 사전을 뒤져서 바로 문서 ID를 찾아냅니다

MYSQL과 ES데이터 정합성문제 발생시 해결방안
- RDBS 와 ES의 데이터 정합성 문제 발생시 RETRY , DEAD LETTER QUEUE를 활용해 재시도 하다가 계속 실패하면 DLQ에 넣어두고 나중에 ES가 복구되면 다시 QUEUE 에서 넣는 방식
- CDC (Change Data Capture) 활용
	**Debezium(데베지움)** 같은 CDC 툴이 이 MySQL의 일기장(binlog)을 몰래 훔쳐보고 있다가, 변경 사항이 생기면 곧바로 Kafka를 통해 ES로 쏴줍니다.
	Spring Boot는 오직 MySQL만 신경 쓰면 됩니다.
- 스케줄링 배치(Batch)를 통한 주기적 보정
	- - **해결:** 새벽 3시같이 트래픽이 적은 시간에 **Spring Batch**를 돌립니다.
	- MySQL의 '어제 하루 주문 건수'와 ES의 '어제 하루 주문 문서 수'를 대조(Validation)합니다.
	- 만약 누락된 데이터가 있다면 MySQL을 기준으로 ES에 부족한 데이터를 강제로 밀어 넣습니다. (덮어쓰기)
  
작성해주신 엄청난 구현 내역과 트러블슈팅, 그리고 시스템의 한계까지 모두 반영하여 오늘 하루를 완벽하게 갈무리하는 **최종 정리본**을 작성해 드립니다.

### 1. 헷갈렸던 점 / 막혔던 점

- **MySQL과 Elasticsearch 간 동기화 정합성 문제:** MySQL 저장 후 ES 저장이 실패했을 때, 전체 데이터를 동기화하기 위해 "롤백(Rollback)하는 방식"을 써야 하는지 고민이 있었습니다. 하지만 메인 DB와 검색용 DB의 성격을 이해하면서 원본 데이터를 건드리는 방식이 아님을 깨달았습니다.
    
- **Kafka 재시도 전략의 기본값 한계:** Spring Kafka 기본 재시도 설정은 간격 없이 빠르게 반복되어 ES 서버가 잠깐 흔들릴 때 금방 소진되는 문제가 있었습니다.
    
- **테스트 환경에서의 인프라 충돌:** H2 내장 DB로 재색인 테스트를 돌릴 때 오토인크리먼트 ID 충돌로 인해 이미 ES에 존재하는 문서 ID와 겹치는 문제가 발생했습니다.
    

### 2. 해결 과정 및 실제 구현 내용 (Deep Dive)

#### ① Retry + DLQ (강건한 비동기 파이프라인 구축)

- **지수 백오프(Exponential Backoff) 적용:** ES 저장이 실패하면 1초, 2초, 4초, 8초 간격으로 최대 4번 재시도하도록 설정하여 서버 부하를 분산했습니다.
    
- **파싱 오류 즉시 차단:** JSON을 읽지 못하는 깨진 메시지는 재시도해도 소용없으므로 재시도 없이 바로 DLT로 직행하도록 Consumer 예외 처리를 개선했습니다.
    
- **DLT 전용 전송기 분리 (더블 스링기파이 이슈 해결):** 기본 Kafka 전송기를 쓰면 JSON 문자열이 `"{...}"`처럼 한 번 더 감싸지는 현상을 발견하여, 원본 그대로를 남기는 DLT 전용 문자열 전송기를 직접 구현했습니다.
    
- **테스트 격리:** 테스트 간 Consumer 그룹 충돌을 방지하기 위해 DLT 테스트마다 매번 새로운 그룹 ID를 할당하도록 처리했습니다.
    

#### ② 새벽 재색인 배치 (OrderReindexJob)

- **`completedAt` 필드 도입:** 주문이 처음 `COMPLETED` 상태가 될 때 시각을 기록하는 컬럼과 인덱스를 추가하여 재색인 대상을 명확히 특정했습니다.
    
- **대용량 처리 최적화:** 전날 완료된 주문을 DB에서 500건씩 끊어 읽어 ES에 재저장하며, 실시간 Kafka 경로와 동일한 변환 로직(`OrderDocument.from(...)`)을 사용하여 정합성을 보장했습니다.
    
- **실행 방식 다변화:** 매일 새벽 3시 30분에 자동 실행되는 크론(Cron) 배치와 수동 실행 API(`POST /api/batch/order-reindex?targetDate=...`)를 모두 구축했습니다.
    
- **MySQL 기반 테스트 환경:** H2 대신 실제 MySQL 컨테이너를 연동하고, 테스트가 끝난 뒤 자기가 만든 ID만 깔끔하게 클린업하는 안전한 통합 테스트를 완성했습니다.
    

### 3. 아직 남은 한계 (Trade-off 인지)

- **기존 완료 주문 마이그레이션:** 과거에 이미 완료된 주문은 `completedAt`이 `NULL`이라 재색인 대상에서 누락되므로, 별도의 마이그레이션 쿼리(`UPDATE orders SET completed_at = created_at WHERE status='COMPLETED' AND completed_at IS NULL`)가 필요합니다.
    
- **DLT 후속 처리:** 현재 DLT에 쌓인 메시지는 원인 조사용 보관함 역할에 그치며, 이를 자동으로 재처리하는 별도의 Consumer나 알림 시스템은 아직 구현 전입니다. (단, 재색인 배치가 DB 기준으로 커버하므로 최종적 일관성은 방어됩니다.)
    
- **재시도 대기 시간 중 블로킹:** 재시도 로직이 동작하는 동안 같은 파티션의 다음 메시지도 함께 대기하므로, 추후 `@RetryableTopic`을 통한 비동기 토픽 재시도 분리가 필요합니다.
    
- **상태 변경 및 삭제 미반영:** 주문이 `COMPLETED`에서 다른 상태로 바뀌거나 삭제된 경우, ES에 남아있는 기존 문서를 지우거나 갱신하는 로직은 아직 추가되지 않았습니다.
