
## 오늘 목표

- RDB(관계형 데이터베이스)와 객체 지향 언어(Java) 사이의 패러다임 불일치를 JPA가 어떻게 해결하는지 이해한다.
- JPA와 Hibernate의 차이를 명확히 구분한다.
- 영속성 컨텍스트(Persistence Context)의 내부 동작(1차 캐시, 쓰기 지연, 변경 감지)을 원리 수준에서 파악한다.

  

## 배운 개념 (내 언어로 설명)
- **JPA (Java Persistence API)**: 자바 진영의 ORM(Object-Relational Mapping) 기술 표준 '명세(인터페이스 모음)'입니다.
    
- **Hibernate**: 그 JPA 명세를 실제로 구현한 가장 대중적인 '구현체(클래스)'입니다.
    
- **Spring Data JPA**: Hibernate를 한 번 더 추상화하여, 개발자가 인터페이스(Repository)만 작성해도 구현체를 동적으로 생성해주는 Spring의 모듈입니다.
	
- **원리 (ORM)** ORM은 자바의 객체(Object)를 DB의 릴레이션(Relation)에 매핑(Mapping)합니다. 개발자가 객체에 데이터를 세팅해서 ORM에 넘기면, ORM이 내부적으로 SQL을 만들어 DB에 실행해줍니다
	
- **핵심 원리 (내부 동작)** 영속성 컨텍스트는 4가지 엄청난 마법을 부립니다.

1. **1차 캐시**: 영속성 컨텍스트 내부에 Map(Key: ID, Value: Entity) 형태의 캐시가 있습니다. 조회 시 DB를 찌르지 않고 1차 캐시부터 뒤집니다.
    
2. **동일성 보장**: 같은 트랜잭션 내에서 같은 ID로 조회한 객체는 완전히 동일한(==) 객체임을 보장합니다.
    
3. **트랜잭션을 지원하는 쓰기 지연(Transactional write-behind)**: 데이터를 저장(persist)할 때마다 바로 INSERT 쿼리를 쏘지 않습니다. 내부의 '쓰기 지연 SQL 저장소'에 쿼리를 차곡차곡 모아둡니다.
    
4. **변경 감지(Dirty Checking)**: 엔티티의 데이터가 변경되면, 개발자가 명시적으로 `update()`나 `save()`를 호출하지 않아도 트랜잭션이 끝날 때 알아서 UPDATE 쿼리를 날립니다
	
	
- Lombok 내부 동작
	Getter, Setter, 생성자 같은 반복적인 자바 코드를 어노테이션(`@Getter`, `@RequiredArgsConstructor`) 하나로 빌드 시점에 자동 생성해주는 라이브러리.

## 헷갈렸던 점 / 막혔던 점

- 만약 트랜잭션(`@Transactional`)이 없는 서비스 로직에서 `menuRepository.findById()`로 객체를 꺼내와서 값을 바꾸면 DB에 업데이트가 될까요? 왜 그럴까요?"
	- 업데이트되지 않습니다. 변경 감지(Dirty Checking)는 영속성 컨텍스트에 있는 엔티티의 스냅샷과 현재 상태를 비교하여 동작하는데, 이 비교와 SQL 생성(flush)은 **트랜잭션이 커밋(Commit)되는 시점**에 발생합니다. `@Transactional`이 없으면 트랜잭션 자체가 시작되지 않고 커밋도 일어나지 않으므로, 자바 객체의 값을 변경하더라도 DB에 반영되지 않습니다.
- build.gradle jpa관련의존성이없어성 jakarta.persistence패키를위해 의존성 추가
	- implementation 'org.springframework.boot:spring-boot-starter-data-jpa'

	-  **"메소드만 호출하면 DB가 알아서 바뀌는 건가요? (`@Transactional`의 중요성)"**
    
    - **막혔던 이유:** 자바 객체의 값을 바꾼 것(`changePrice`)과 실제 DB에 쿼리가 나가는 시점이 분리되어 있다는 개념이 생소했기 때문입니다.
        
    - **해결 포인트:** `changePrice()`는 메모리 상의 값만 바꾸는 평범한 메서드이며, 영속성 컨텍스트의 변경 감지(Dirty Checking)와 트랜잭션 커밋(Commit)이라는 방아쇠가 당겨져야만 비로소 `UPDATE` 쿼리가 나간다는 것을 몸소 확인했습니다.
        
- **"H2 콘솔 접속할 때 자꾸 파일 경로 에러(`Database not found`)가 나요!"**
    
    - **막혔던 이유:** Spring Boot가 바라보는 파일 DB 경로(`./data/kds_db`)와 웹 브라우저의 H2 콘솔 창이 기본으로 접근하려던 경로(`~/test`)가 달라서 발생한 전형적인 설정 불일치 문제였습니다.
        
    - **해결 포인트:** H2 콘솔 로그인 창의 JDBC URL을 application.yml에 적어둔 주소와 정확히 일치시켜 해결하는 법을 익혔습니다.
