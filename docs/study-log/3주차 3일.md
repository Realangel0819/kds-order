## 오늘 목표
- **오늘의 학습 목표:** SSE(Server-Sent Events)의 동작 원리를 이해하고, Spring WebFlux 환경에서 스트리밍 API를 설계합니다.
    
- **왜 배우는가?** 주방 모니터는 사용자가 '새로고침'을 누르지 않아도 새 주문이 들어오면 화면에 바로 떠야 합니다. 이를 위한 실시간 통신 기술을 익힙니다.
    
- **프로젝트 적용:** 어제 만든 Batch Grouping의 결과물을 KDS 화면에 실시간으로 Push 해주는 기능에 사용합니다.-

  

## 배운 개념 (내 언어로 설명)

- Server Service Client  : 서버클라이언트의 새로고침없이 새로운정보 추가시 계속 단방향으로 push해주는 기술
- HTTP 프로토콜에서 동작하며 client랑 server가 연결을 한번 맺으면 데이터를 지속적으로 스트리밍할 수 있도록 하는 w3c 표준 웹 api임
	- 사용하지않을시에 handshake비용 발생 계속 연결을 하고 잦은 요청과 연결을 맺고 끊어여함
- KDS가 한번 get stream요청하면 web-flux는 http연결을 닫지않고 계속유지함
	- 이벤트가 생기면 연결을 통해 data {} 형태로 텍스트를 계속 흘려보냄 연결 끊을 때까지 4,5회반복
- **Nginx / AWS ALB의 Timeout:**
    
    - 앞단에 있는 로드밸런서나 리버스 프록시(Nginx)는 보통 HTTP 연결이 60초 정도 응답이 없으면 연결을 끊어버립니다(Idle Timeout). 이를 방지하기 위해 주기적으로 빈 데이터(Heartbeat/Ping)를 쏴주어야 합니다.
        
- **서버가 여러 대(Scale-Out)일 때의 문제:**
    
    - 현재 구조의 한계: 만약 알림 서버가 A, B 2대라고 가정해봅시다. KDS 기기는 서버 A에 SSE 연결을 맺고 있습니다. 그런데 Batch Grouping 처리 결과가 서버 B에서 생성된다면? 서버 B는 어떻게 서버 A에 붙어있는 KDS로 데이터를 Push 할 수 있을까요?
        
    - 해결책: 이럴 때 **Redis Pub/Sub**이나 **Kafka**를 활용해 모든 알림 서버로 이벤트를 브로드캐스팅하는 아키텍처가 필요해집니다. (우리 프로젝트에서도 면접 방어용으로 설계적 고민을 해두어야 하는 부분입니다.)



타이머(`Flux.interval`)가 아니라, **외부(Kafka Consumer)에서 특정 메서드를 호출했을 때 그 데이터를 현재 연결된 SSE `Flux` 스트림으로 밀어 넣으려면** 어떻게 해야 할까요?

이때 WebFlux에서 제공하는 것이 바로 **`Sinks`** 입니다.

Sink는 기본적으로 동시 방출(Concurrent Emit)에 대해 Thread-safe하지 않습니다. 여러 스레드에서 동시에 `tryEmitNext`를 호출하면 하나는 실패합니다.
  

## 헷갈렸던 점 / 막혔던 점

KDS 화면 실시간 알림 부분에서, "KDS 화면이 직접 Kafka Topic을 컨슘(Consume)하게 만들지 않고, 굳이 WebFlux 알림 서버를 중간에 띄워서 SSE로 전달해야 하는 이유"는 무엇일까요?
- KDS 클라이언트는 일반적으로 앱이나 웹브라우저로 http 웹 표준 프로토콜을 사용하는데 kafka같은거는 tcp기반 바이너리 프로토콜을 사용함 // 앱에서는 직접 kafka 브로커에 접근할 방법이 없음 webflux를 통해서 웹언어로 번역해주어야함 // kakfa 브로커의 ip와 포트를 퍼블릭망에 계속 열어두어야하는데 보안위험 및 구조적 결함이 발생할 수있음
- kafka 컨슈머는 1:1, 1:N으로 매핑되어 주기적으로 데이터를 polling 하는 무거운 client기 때문에 버티지못함 하지만 webflux는 이벤트 루프 기반이라 non blocking 형식으로 많은 데이터 이동가능

batch grouping 완성 -> kafka topic 발행(알림용) -> webflux서버 (notification server & consumer server) -> 수천개 KDS 와 맺어진가벼운 SSE (http)통신으로 data push



**1. KDS 알림을 구현할 때 WebSocket 대신 SSE를 선택한 기술적 이유는 무엇인가요?**

- **작성하신 답:** websocket은 데이터 폴링시 연결 유지비용이 너무 큼 sse는 계속 연결을 유지하고 보내면돼서 대용량 단방향통신에 유리
    
- **💡 면접관 교정:** WebSocket은 '폴링'이 아닙니다. WebSocket과 SSE 둘 다 연결을 유지하는 기술입니다.
    
    - **정답:** "KDS는 서버로부터 주문 알림을 받기만 하는 **단방향 통신**이면 충분합니다. WebSocket은 양방향 통신을 지원하여 무겁고 별도의 프로토콜(`ws://`)을 처리해야 하지만, SSE는 가벼운 HTTP 기반이며 브라우저 자체적으로 자동 재연결(Auto-Reconnect)을 지원하기 때문에 KDS 알림 시스템에 훨씬 적합하고 리소스 효율적이라고 판단했습니다."
        

**2. SSE 연결 시 로드밸런서(Nginx/ALB) 등에서 60초 뒤에 연결이 끊기는 현상을 어떻게 방어하셨나요?**

- **작성하신 답:** 60초동안 안쓰면 끊기는거 방지를위해서 heartbeat를 1초마다 보내서 계속 유지하게함
    
- **💡 면접관 교정:** 훌륭합니다! "Nginx나 AWS ALB의 Idle Timeout에 의해 연결이 끊기는 것을 방어하기 위해, 서버 측에서 일정 주기(예: 30초)마다 의미 없는 더미 데이터(`heartbeat`)를 Push하여 커넥션이 활성 상태임을 인프라에 알려주도록 구현했습니다." 라고 다듬으면 완벽합니다.
    

**3. WebFlux의 Sinks를 사용할 때, 기본 설정인 `autoCancel=true`를 그대로 두면 실무에서 어떤 장애가 발생할 수 있나요?**

- **작성하신 답:** autocancel을 true로 하면 다음날 보내려고 할떄 연결이 끊겨잇는 문제발생 ?잘모르겟다 자세히 설명해줘
    
- **💡 면접관 교정:** 이 부분은 꼭 이해해야 합니다.
    
    - **개념:** `autoCancel=true`는 "마지막 남은 1명의 구독자(KDS)마저 연결을 끊으면, Sinks 파이프 자체를 폭파(Complete)시킨다"는 뜻입니다.
        
    - **장애 상황:** 밤 10시에 영업이 끝나고 전국의 KDS 태블릿 전원을 모두 껐다고 가정해 보세요. 알림 서버의 구독자는 '0명'이 됩니다. 이때 파이프가 폭파됩니다. 다음 날 아침 9시에 KDS를 다시 켜도, 알림을 쏴줄 파이프가 이미 사라졌기 때문에 서버를 재시작하기 전까지 아무도 알림을 받을 수 없는 대형 장애가 발생합니다.
        
    - **해결:** 그래서 `autoCancel=false`로 설정하여, 구독자가 0명이 되더라도 파이프(Sink)를 유지하도록 만들어야 합니다.
        

**4. KDS 클라이언트(프론트엔드)가 직접 Kafka Topic을 Consume하지 않고, 중간에 WebFlux 서버를 둔 이유는 무엇인가요?**

- **작성하신 답:** kds는 웹기반 프로토콜이라서 tcp기반 kafka를 쓰려면 번역해주는 중간다리역할이 필요
    
- **💡 면접관 교정:** 아주 좋습니다! 여기에 '보안'과 '커넥션 한계'를 덧붙이면 더 좋습니다. "KDS는 HTTP 등 웹 프로토콜만 이해할 수 있어 TCP 기반의 Kafka에 직접 붙을 수 없습니다. 또한 수천 대의 KDS가 직접 Consumer Group을 형성하면 Kafka 브로커에 심각한 부하와 인프라 보안 위협이 발생하므로, WebFlux를 중간 API 게이트웨이처럼 두어 책임을 분리했습니다."
    

**5. 알림 서버가 3대로 Scale-Out 되었습니다. 3대 모두 동일한 알림을 Kafka로부터 전달받으려면 Consumer Group 설정을 어떻게 해야 하며, 그 이유는 무엇인가요?**

- **작성하신 답:** consumer server 그룹을 그룹아이디를 모두 다르게하고 broadcast하면됨
    
- **💡 면접관 교정:** 완벽합니다! "Kafka는 동일한 `group.id`를 가진 컨슈머들에게 메시지를 분산(Load Balancing)시켜버립니다. 알림 서버는 각자 연결된 KDS 클라이언트들을 관리하고 있으므로, 모든 알림 서버가 100% 동일한 메시지를 받아야(Broadcasting) 합니다. 따라서 각 서버가 기동될 때마다 UUID 등을 활용해 고유한 `group.id`를 가지도록 설정했습니다."
    

### 🧠 복습 퀴즈 정답 확인

1. **SSE 요청 시 서버가 응답해야 하는 HTTP 헤더의 `Content-Type`은 무엇인가요?**
    
    - 당신의 답: get ❌
        
    - **정답:** `text/event-stream` (GET은 HTTP 메서드입니다.)
        
2. **Kafka에서 같은 `group.id`를 가진 컨슈머들에게 메시지를 찢어서 분배하는 것을 무엇이라고 부르나요?**
    
    - 당신의 답: 모르겟어 ❌
        
    - **정답:** 로드 밸런싱 (Load Balancing) 또는 컨슈머 그룹 리밸런싱 (Rebalancing).
        
3. **Sinks 파이프에 데이터를 강제로 밀어 넣을 때 사용하는 메서드 이름은 무엇인가요?**
    
    - 당신의 답: tryEmitNext? ⭕️
        
    - **정답:** `tryEmitNext()` 맞습니다!
        
4. **브라우저가 SSE 연결을 유지하고 있는 상태에서 서버가 강제로 재시작되었습니다. 브라우저의 SSE 클라이언트(`EventSource`)는 영원히 끊긴 상태로 남을까요? (O/X)**
    
    - 당신의 답: X? ⭕️
        
    - **정답:** X. SSE의 가장 강력한 장점 중 하나가 브라우저 단에서 자동 재연결(Auto-Reconnect)을 시도한다는 것입니다.
        
5. **다수의 클라이언트가 오랜 시간 연결(Connection)을 유지하고 아무것도 안 하고 대기(Idle)하는 상황이라면, Spring MVC(Tomcat)와 Spring WebFlux(Netty) 중 어느 것이 메모리/스레드 자원 관리에 유리할까요?**
    
    - 당신의 답: webflux가 유리 mvc는 연결을 유지하기위한 ㅁ비용이 많이듬 blocing ⭕️
        
    - **정답:** 완벽합니다. Spring MVC(Tomcat)는 1 커넥션 = 1 스레드(Thread-per-request)를 차지하여 대기(Blocking)하므로 스레드 풀이 고갈되기 쉽습니다. WebFlux(Netty)는 이벤트 루프를 사용해 비동기 논블로킹으로 동작하므로 적은 스레드로 수만 개의 유휴 커넥션을 유지할 수 있습니다.
