
## 오늘 목표

- **오늘의 학습 목표:** 멀티스레드 환경에서 발생하는 Race Condition(경쟁 상태)의 원리를 이해하고, 테스트 코드를 통해 데이터 오염(Lost Update)을 직접 재현합니다.
    
- **왜 배우는가:** 동시성 제어(분산락 등)를 적용하기 전에, **문제가 존재한다는 것**을 먼저 증명해야 해결책의 가치가 생기기 때문입니다.
    
- **프로젝트 적용:** 100개의 주문이 동시에 들어올 때, 일일 누적 주문량이나 특정 메뉴의 주문 카운트가 락이 없을 때 어떻게 망가지는지 확인합니다.
  

## 배운 개념 (내 언어로 설명)

- 가장 대표적인 동시성 문제는 **Lost Update (갱신 손실)**
- - **`ExecutorService`**: 여러 스레드를 병렬로 띄워서 동시에 작업을 실행하게 해주는 스레드 풀 관리자입니다.
    
- **`CountDownLatch`**: 여러 스레드의 작업이 모두 끝날 때까지 메인 스레드가 기다리도록(대기) 해주는 동기화 도구입니다. 출발선에서 총소리를 기다렸다가 동시에 출발하고, 결승선에 모두 들어올 때까지 기다리는 역할을 합니다.
`Main Thread (테스트 실행)` ↓ `ExecutorService`가 100개의 `Worker Thread` 생성 ↓ 100개의 스레드가 동시에 `OrderService.createOrder()` 호출 (공유 데이터 접근) ↓ `CountDownLatch`가 100개의 작업이 끝날 때까지 대기 ↓ 모두 끝나면 `DB`에서 최종 카운트 조회 → **예상값(100)과 실제값(ex: 34) 비교 (데이터 오염 확인)**


#### 실무에서 발생하는 문제

- **증명 없는 도입:** 주니어 개발자들이 흔히 하는 실수 중 하나가 "동시성 문제가 생길까 봐 락을 걸었어요"라고 말하면서, **락이 없을 때 데이터가 얼마나 깨지는지 테스트를 안 해보는 것**입니다. 실무에서는 버그를 잡을 때 '재현(Reproduce)'이 가장 중요합니다. 재현할 수 없는 문제는 해결된 건지도 증명할 수 없기 때문입니다


자바에서 `Future` 객체를 한 문장으로 비유하자면 "카페에서 주문하고 받는 진동벨"입니다
Future future = executorService.submit(() -> { ... }); 


  

**1. 문제 1: 비동기 스레드의 예외 삼킴(Exception Swallowing) 현상**

- **막혔던 점:** `ExecutorService.submit()`을 이용해 100개의 비동기 스레드로 동시성 테스트를 실행했을 때, 내부 로직에서 에러가 발생해도 콘솔에 에러 로그가 찍히지 않고 조용히 테스트가 종료되거나 실패하는 현상을 겪었습니다. 이로 인해 어떤 스레드에서 무슨 에러가 났는지 원인을 파악하기 어려웠습니다.
    
- **해결 과정:** 비동기 작업의 결과를 담는 `Future` 객체의 특징을 활용했습니다. 각 스레드의 작업 결과를 `List>`에 담은 뒤, 테스트 마지막에 `future.get()`을 호출하여 백그라운드 스레드에서 발생한 예외를 메인 테스트 스레드로 강제로 끌어올렸습니다(Throw). 그 결과, 묻혀있던 예외 메세지를 확인하여 다음 문제의 실마리를 잡을 수 있었습니다.
    

**2. 문제 2: 100을 기대했으나 98이 저장되는 간헐적 실패 (Flaky Test)**

- **막혔던 점:** 분산락을 적용했음에도 최종 주문 수가 100이 아닌 98이 나오는 등, 실행할 때마다 결과가 달라지는 불안정한 테스트(Flaky Test) 현상을 마주했습니다.
    
- **해결 과정:** `future.get()`으로 끌어올린 로그를 분석한 결과, `java.lang.IllegalStateException: 락 획득 실패 (요청 폭주)` 에러를 확인했습니다. 원인은 Redisson의 `tryLock` 파라미터 중 대기 시간(`waitTime`)이었습니다. 컴퓨터의 CPU 컨디션에 따라 100개의 스레드가 순차적으로 락을 얻고 반환하는 데 걸리는 총시간이 `waitTime`을 초과하는 순간이 있었고, 줄 서서 기다리던 마지막 스레드 2개가 타임아웃으로 튕겨 나가면서 유실이 발생한 것을 파악했습니다.
    

**3. 문제 3: 타임아웃(Timeout)의 비즈니스적 판단과 에러 강제 재현**

- **막혔던 점:** 디버그 코드를 지우니 다시 100으로 성공하는 현상(하이젠버그 현상)이 발생하여, 이것이 완벽히 해결된 것인지 단순한 운(CPU 컨디션)인지 검증이 필요했습니다.
    
- **해결 과정:** 운에 맡기지 않기 위해, 락의 `waitTime`을 0초로 극단적으로 줄이거나 서비스 로직 내부에 `Thread.sleep(100)`을 주어 **강제로 타임아웃 에러를 100% 재현**하는 테스트를 진행했습니다. 시스템이 의도한 대로 타임아웃을 발생시킴을 확인한 후, 비즈니스 요구사항("주문 카운트는 무조건 누락 없이 100% 처리되어야 한다")에 맞춰 `waitTime`을 넉넉하게 늘려 동시성 처리 정합성을 100% 확보했습니다.
