
## 오늘 목표

- **이해해야 할 것:** 계층형 아키텍처(Layered Architecture)의 원칙과 의존성 방향, 단일(Monolithic) 구조의 한계와 서비스를 분리해야 하는 이유를 명확히 이해합니다.
    
- **배우는 이유:** 코드가 단순히 '돌아가게' 만드는 것을 넘어, 변경에 유연하고 트래픽 폭주 시 특정 도메인의 장애가 전체 시스템으로 전파되지 않게 설계하기 위함입니다.
    
- **프로젝트 적용점:** 현재 하나의 프로젝트에 뭉쳐있는 코드를 내일(Day 4) `order-service`와 `menu-service` 모듈로 쪼개기 위한 이론적 근거(명분)를 마련합니다.
    
- **증명해야 할 것:** 면접관에게 "왜 Order와 Menu를 굳이 나누었나요?"라는 질문을 받았을 때, 타당한 비즈니스 및 기술적 근거를 제시할 수 있어야 합니다.

  

## 배운 개념 (내 언어로 설명)

- 계층형 아키텍처와 서비스 분리
	- Layered Architecture (관심사분리 SoC) : controller service repository로 나누어서 의존성의 단방향화
	- Microservices Architecture서비스분리 : 단일코드베이스 (monolith) 를 비즈니스단위 독립아키텍쳐로 분리
- 단일구조의한계
	- 장애전파 : 한곳트래픽 폭주하면 다른곳도 터짐
	- 확장성의 비효율 : 특정 파트만 늘리고 싶어도 다른거 까지 다커짐
- 핵심원리
	- 단방향의존성 : 계층간 서로 몰라야함
	- 도메인분리 : 데이터 소유권을 명확하게하고 필요한데이터는 API(ex) gRPC)에 물어봐야함

### 실무에서 발생하는 문제

초보 개발자들은 '서비스 분리(MSA)'가 무조건 좋은 줄 알고 처음부터 무작정 쪼갭니다. 그러나 서비스를 쪼개는 순간 **분산 트랜잭션, 네트워크 지연, 데이터 동기화**라는 엄청난 기술적 복잡도가 폭발합니다. 그래서 우리는 단일 모듈로 먼저 동작 원리를 익히고(Day 1~2), 한계를 명확히 정의한 후 쪼개는(Day 3~4) 방식을 택하는 것입니다.

- `Monolith` ↔ `Microservices` ↔ `Multi-Module`: 멀티 모듈은 코드를 나누는 것이고, 마이크로서비스는 런타임(서버)을 나누는 것입니다.
    
- `Layered Architecture` ↔ `Clean Architecture`: 계층형 구조에서 더 나아가 도메인을 보호하기 위한 진화된 형태들입니다.


### Menu Service

```
핵심 책임
- 메뉴 정보 및 가격 관리
- 조리 메타데이터 관리
  - 조리시간
  - 필요한 조리 도구
  - 최대 조리 가능 수
- 판매 상태 관리
```

### Order Service

```
핵심 책임
- 주문 생성 및 유효성 검증
- 주문 상품 및 수량 관리
- 주문 상태 관리
- 주문 생성 시간 관리
- 주문 당시 필요한 메뉴 정보의 snapshot 관리
```
