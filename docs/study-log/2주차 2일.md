## 오늘 목표

- **오늘의 학습 목표:**  DynamoDB의 핵심 개념(Partition Key, Sort Key)을 이해하고, 조회 이벤트를 저장하기 위한 NoSQL 테이블 설계법(Access Pattern)을 익힌다.
- **왜 배우는가?:** 관계(Join)나 복잡한 트랜잭션이 필요 없고, 단기간에 데이터가 폭발적으로 쌓이는 이벤트/로그성 데이터를 MySQL에 넣는 것은 비효율적입니다. 이런 데이터는 무한히 확장 가능하고 엄청나게 빠른 NoSQL에 저장하는 것이 적합합니다
  

## 배운 개념 (내 언어로 설명)

- DynamoDB와 NoSQL 모델링
	- 어떤크기의 트래픽이몰려와도 무한히서버를늘려 밀리초단위 응답속도보장
	- AWS에서제공하는 분산형 데이터베이스 서비스
	- 데이터를 여러 파티션에 분산 저장하여 높은 처리량(Throughput)과 짧은 지연 시간(Latency)을 보장
	- 복잡한 Join과 트랜잭션을 포기하더라도, 트래픽이 아무리 늘어나도 절대 죽지 않고 10ms 이하로 응답하는 저장소를 만들자라는 목표로 탄생
- **Partition Key (PK):** 이 데이터가 "어느 물리적 컴퓨터(파티션)에 저장될지" 결정하는 해시(Hash) 키입니다.
- **Sort Key (SK - 선택):** 같은 파티션 내부에 저장된 데이터들을 "어떤 기준으로 정렬할지" 결정하는 키입니다.
- **PK (Partition Key):** `MENU#101` (메뉴 ID)
- **SK (Sort Key):** `EVENT#2026-09-21T10:00:00` (이벤트 발생 시간)
- **Attributes:** `UserId`, `Source(앱/웹)` 등
- **매우 중요한 한계점입니다.** (면접 단골) 우리가 PK를 `MenuId`로 잡았습니다. 그런데 만약 "뿌링클 치킨"이 TV 예능에 나와서 전국민이 뿌링클 치킨(MENU#101)만 조회한다면 어떻게 될까요? 해시 함수에 의해 `MENU#101`은 단 **하나의 특정 파티션**에만 저장되게 됩니다. 전체 DB 서버는 100대인데, 1번 서버(파티션)에만 트래픽이 100% 몰리는 현상. 이를 **Hot Partition**이라고 합니다. _(프로젝트의 한계로 반드시 인지해야 합니다. 완화하려면 PK 뒤에 난수 0~9를 붙여서 `MENU#101-3`처럼 파티션을 강제로 분산시키는 Write Sharding 기법을 씁니다.)_

**Q1. MySQL(RDB)과 비교했을 때 DynamoDB(NoSQL)의 조회 방식은 어떻게 다른가요?**

> **모범 답안:** "MySQL은 데이터 간의 관계를 정의하고 Join과 다중 컬럼 조건을 통해 **유연한 쿼리**가 가능합니다. 반면 DynamoDB는 Join이 불가능하고, 오직 사전에 정의된 **PK(Partition Key)와 SK(Sort Key)를 기준으로만 데이터를 조회**할 수 있습니다. 즉, 유연성을 포기한 대신 데이터가 페타바이트급으로 늘어나도 **항상 10ms 이하의 일관된 응답 속도**와 무한한 확장을 보장한다는 것이 가장 큰 차이입니다."

**Q2. DynamoDB에서 Query와 Scan 연산의 차이점은 무엇인가요?**

> **모범 답안:** "가장 큰 차이는 **파티션 접근 방식**입니다. **Query**는 PK 값을 해시 함수에 통과시켜 데이터가 있는 물리적 파티션을 정확히 찾아가서 읽으므로 속도가 매우 빠르고 일정합니다. 반면 **Scan**은 PK 조건 없이 전체 파티션의 모든 데이터를 처음부터 끝까지 다 뒤지는 풀 스캔(Full Scan) 방식입니다. 실무에서 Scan을 사용하면 심각한 성능 저하와 막대한 요금 폭탄이 발생하므로, 반드시 Query를 사용할 수 있도록 PK/SK(Access Pattern) 설계를 잘하는 것이 핵심입니다."

**Q3. 특정 메뉴에 트래픽이 폭주할 경우 발생하는 Hot Partition(핫 파티션) 문제는 무엇이며 어떻게 해결하나요?**

> **모범 답안:** "Hot Partition은 특정 PK(예: 유명해진 치킨 메뉴 ID)에만 트래픽이 집중되어, **전체 분산 서버 중 단 하나의 물리적 파티션에만 부하가 몰려 병목이 발생하는 현상**입니다. 이를 해결하기 위해 **'쓰기 샤딩(Write Sharding)'** 기법을 사용합니다. PK 뒤에 0부터 9까지의 난수(Random Number)를 접미사로 붙여서(예: `MENU#101-3`), 데이터를 여러 물리적 파티션으로 강제로 분산 저장함으로써 특정 노드에 트래픽이 쏠리는 것을 방지할 수 있습니다."


## 헷갈렸던 점 / 막혔던 점

- DynamoDbConfig가 컴파일되지 않았습니다.
  - package와 import가 하나도 없어서 Configuration, Bean, DynamoDbEnhancedClient를 못
    찾는다는 오류가 3개 났습니다.
  - 클래스 본문만 복사해 붙여넣고 파일 맨 위를 빠뜨린 것이 원인입니다.
- dynamodb-enhanced:2.20.+ 버전이 고정되지 않았습니다.
  - +는 "2.20 중 최신"이라 빌드할 때마다 버전이 달라질 수 있어, 어제는 되던 빌드가 오늘
    깨질 수 있습니다.
- Entity의 어노테이션 위치가 헷갈렸습니다.
  - @DynamoDbPartitionKey는 필드가 아니라 getter에 붙여야 합니다.
  - DynamoDB Enhanced Client가 필드가 아니라 getter/setter를 리플렉션으로 읽기 때문입니다.
- 로컬 DynamoDB의 menu_views 테이블이 없었습니다.
  - 컨테이너를 새로 띄우면 깡통 상태이고, -inMemory 옵션이라 재시작하면 데이터도
    사라집니다.
- Kafka 연결 오류가 계속 반복됐습니다.
  - 로그에 Connection to node -1 (localhost:9092) could not be established가 무한
    반복됐습니다.
  - 코드 오류처럼 보이지만, 실제로는 브로커가 죽어 있었습니다.

해결 과정

1. DynamoDbConfig: package와 import를 추가하니 컴파일이 통과했습니다.
2. 버전 고정: 2.20.+를 2.20.162로 바꿨습니다.
3. Entity/Repository/Consumer 구현: 요구사항 명세대로 작성했습니다. 테이블은
   @PostConstruct에서 없으면 만들도록 했습니다.
4. Kafka 연결 문제 추적:
   - docker ps -a로 보니 zookeeper와 kafka가 둘 다 Exited (1) 상태였습니다.
   - docker logs로 확인하니 Zookeeper가 JMX 에이전트 NullPointerException으로 먼저 죽었고,
     Kafka는 zookeeper:2181을 찾지 못해 따라서 죽은 것이었습니다.
   - cp-zookeeper:7.3.0 이미지가 최신 Docker Desktop/WSL 환경에서 이 오류가 나는 것으로
     알려져 있어, Zookeeper가 필요 없는 KRaft 모드(apache/kafka:3.8.0)로 교체했습니다.
   - 교체 후 실행 중이던 앱의 컨슈머가 자동으로 재연결됐습니다.

교훈: 연결 오류가 나면 코드보다 먼저 docker ps -a와 docker logs로 인프라가 살아 있는지
확인하세요. 오류가 반복돼도 근본 원인은 맨 처음 죽은 컨테이너 하나인 경우가 많습니다.

코드 동작 설명 (Java 클래스 중심)

전체 흐름

Postman: GET /api/menus/1
   │
   ▼
MenuController.getMenu()          ← HTTP 요청을 받음
   │
   ▼
MenuService.getMenu()             ← H2에서 메뉴 조회
   │  성공하면
   ▼
MenuViewProducer.sendMenuViewEvent()   ← Kafka로 "조회됐다" 메시지 발행
   │
   ▼  (Kafka 토픽: menu-view-topic)
   │
MenuViewConsumer.consumeMenuViewEvent()   ← Kafka에서 메시지 수신
   │  JSON → MenuViewEvent → MenuViewEntity
   ▼
MenuViewRepository.save()         ← DynamoDB(menu_views)에 저장

핵심은 조회 API의 응답과 DynamoDB 저장이 분리되어 있다는 점입니다. 사용자는 메뉴를 받자마자
응답을 받고, 조회 기록 저장은 Kafka를 통해 뒤에서 비동기로 처리됩니다.

클래스별 설명

1. MenuController (진입점)

- @RestController: 이 클래스의 메서드 반환값이 HTTP 응답 본문(JSON)이 된다는 뜻입니다.
- @GetMapping("/{menuId}"): GET /api/menus/1이 오면 getMenu(1)이 실행됩니다.
- 하는 일은 menuService.getMenu(menuId)를 호출해 결과를 반환하는 것뿐입니다. 컨트롤러는
  요청을 받아 서비스에 넘기는 역할만 합니다.

2. MenuService (비즈니스 로직)

Menu menu = menuRepository.findById(menuId)
        .orElseThrow(() -> new MenuNotFoundException(menuId));
try {
    menuViewProducer.sendMenuViewEvent(menuId);
} catch (Exception e) {
    log.error(...);   // 실패해도 삼킴
}
return menu;
- 먼저 H2 DB에서 메뉴를 찾고, 없으면 MenuNotFoundException을 던집니다.
- 조회에 성공하면 Kafka로 이벤트를 발행합니다.
- try-catch로 예외를 삼키는 이유: Kafka가 죽어도 메뉴 조회 자체는 성공해야 하기 때문입니다.
  부가 기능(조회 기록)이 핵심 기능(메뉴 반환)을 망치면 안 됩니다.

3. MenuViewEvent (DTO, record)

public record MenuViewEvent(Long menuId, LocalDateTime viewedAt) {}
- DTO(Data Transfer Object): 데이터를 실어 나르는 용도의 객체입니다.
- record는 불변 데이터 클래스를 짧게 쓰는 문법입니다. 생성자, getter(menuId(), viewedAt()),
  equals, toString이 자동으로 만들어집니다.
- Kafka 메시지의 모양(JSON 구조)을 정의합니다.

4. MenuViewProducer (Kafka 발행)

private final KafkaTemplate<String, Object> kafkaTemplate;

MenuViewEvent event = new MenuViewEvent(menuId, LocalDateTime.now());
kafkaTemplate.send(TOPIC, String.valueOf(menuId), event);
- KafkaTemplate은 Spring이 제공하는 Kafka 전송 도구입니다. @RequiredArgsConstructor가
  생성자를 만들면 Spring이 자동으로 주입해 줍니다(의존성 주입, DI).
- send(토픽, 키, 값)의 세 인자:
  - 토픽: 메시지를 보낼 채널 이름(menu-view-topic)입니다.
  - 키: menuId를 문자열로 바꾼 값입니다. 같은 키의 메시지는 같은 파티션으로 가서 순서가
    보장됩니다.
  - 값: MenuViewEvent 객체입니다. application.properties의 JsonSerializer가 이 객체를 JSON
    문자열로 바꿔 전송합니다.

5. MenuViewConsumer (Kafka 수신, 오늘의 핵심)

@KafkaListener(topics = "menu-view-topic", groupId = "menu-group")
public void consumeMenuViewEvent(String message) {
    MenuViewEvent event = objectMapper.readValue(message, MenuViewEvent.class);
    MenuViewEntity entity = new MenuViewEntity(
            event.menuId(),
            event.viewedAt().format(DateTimeFormatter.ISO_LOCAL_DATE_TIME),
            "test-user");
    menuViewRepository.save(entity);
}
- @KafkaListener: 앱이 뜨면 Spring이 백그라운드 스레드로 이 토픽을 계속 감시하고, 메시지가
  오면 이 메서드를 자동으로 호출합니다. 직접 호출하는 코드는 어디에도 없습니다.
- groupId: 같은 그룹의 컨슈머끼리는 메시지를 나눠 받습니다. 그룹 ID가 같으면 같은 메시지를
  중복 처리하지 않습니다.
- 값은 String으로 받습니다. application.properties에서 컨슈머의 value-deserializer를
  StringDeserializer로 설정했기 때문입니다.
- ObjectMapper.readValue(): JSON 문자열을 자바 객체로 바꾸는 Jackson 라이브러리입니다.
  역직렬화라고 부릅니다(객체 → JSON은 직렬화).
- DTO → Entity 변환: 수신용 객체(MenuViewEvent)와 저장용 객체(MenuViewEntity)는 역할이 달라
  분리했습니다. LocalDateTime은 DynamoDB에 저장하기 어려워 ISO-8601 문자열로 바꿉니다.
- JSON 파싱에 실패하면(JsonProcessingException) 에러 로그만 남기고 넘어갑니다.

6. MenuViewEntity (DynamoDB에 저장되는 모양)

@DynamoDbBean
public class MenuViewEntity {
    private Long menuId;
    private String viewedAt;
    private String userId;

    @DynamoDbPartitionKey
    public Long getMenuId() { ... }

    @DynamoDbSortKey
    public String getViewedAt() { ... }
}
- @DynamoDbBean: DynamoDB Enhanced Client에게 "이 클래스를 테이블 행으로 매핑해도 된다"고
  알리는 표시입니다. 기본 생성자와 getter/setter가 반드시 필요해서 Lombok
  @NoArgsConstructor, @Getter, @Setter를 썼습니다.
- 파티션 키(menuId): DynamoDB가 데이터를 어느 서버(파티션)에 저장할지 정하는 키입니다.
- 정렬 키(viewedAt): 같은 파티션 안에서 정렬 순서를 정하는 키입니다.
- 두 키를 합친 조합이 한 행의 고유 식별자가 됩니다. 그래서 같은 메뉴를 여러 번 조회해도
  시간이 다르면 각각 별도 행으로 쌓입니다.

7. MenuViewRepository (DynamoDB 접근)

public MenuViewRepository(DynamoDbEnhancedClient enhancedClient) {
    this.table = enhancedClient.table("menu_views",
TableSchema.fromBean(MenuViewEntity.class));
}

@PostConstruct
void createTableIfNotExists() {
    try { table.describeTable(); }
    catch (ResourceNotFoundException e) { table.createTable(); }
}

public void save(MenuViewEntity entity) { table.putItem(entity); }
- DynamoDbEnhancedClient는 자바 객체를 그대로 DynamoDB에 넣고 뺄 수 있게 해 주는
  도구입니다. DynamoDbConfig가 빈으로 등록해 두었기 때문에 주입받을 수 있습니다.
- TableSchema.fromBean(...)은 Entity의 어노테이션을 읽어 "이 클래스는 이런 테이블
  구조다"라는 설계도를 만듭니다.
- @PostConstruct: 객체가 만들어지고 의존성 주입까지 끝난 직후 딱 한 번 실행됩니다. 여기서
  테이블이 있는지 describeTable()로 확인하고, 없으면(ResourceNotFoundException)
  createTable()로 만듭니다.
- putItem: 행을 하나 넣습니다. 같은 키가 이미 있으면 덮어씁니다.

8. DynamoDbConfig (연결 설정)

@Configuration
public class DynamoDbConfig {
    @Bean
    public DynamoDbEnhancedClient dynamoDbEnhancedClient() { ... }
}
- @Configuration은 이 클래스가 Spring 설정 클래스임을 뜻합니다.
- @Bean은 이 메서드가 반환한 객체를 Spring 컨테이너에 등록합니다. 그래야
  MenuViewRepository가 생성자에서 DynamoDbEnhancedClient를 받을 수 있습니다.
- 안에서 endpointOverride("http://localhost:8000")으로 실제 AWS 대신 로컬 컨테이너를가리키게 하고, dummy 자격 증명을 넣었습니다.

꼭 이해해야 할 개념 3가지

1. 의존성 주입(DI): new로 직접 만들지 않고 Spring이 만들어서 생성자로 넣어 줍니다. 위의 @RequiredArgsConstructor와 @Bean이 모두 이 원리로 연결됩니다.
2. 직렬화 / 역직렬화: Producer는 객체 → JSON(JsonSerializer), Consumer는 JSON → 객체(ObjectMapper)로 바꿉니다. Kafka는 바이트만 전달하기 때문에 이 변환이 필요합니다.
3. 비동기 분리: 조회 응답과 DynamoDB 저장이 Kafka로 분리되어 있어서, DynamoDB가 느리거나 죽어도 메뉴 조회 응답은 영향을 받지 않습니다.

직접 확인해 보는 순서

1. docker compose up -d로 Kafka와 DynamoDB를 띄웁니다.
2. menu-service를 실행합니다. DynamoDB 테이블 생성 완료 로그가 나와야 합니다.
3. 메뉴를 만들고 조회합니다. POST /api/menus?name=김치찌개&price=9000&cookingTime=10 후 GET /api/menus/1을 호출합니다.
4. 로그 순서를 확인합니다. 메뉴 조회 이벤트 발행 완료 다음에 DynamoDB 적재 완료가 나와야 합니다.
5. 같은 메뉴를 여러 번 조회한 뒤 aws dynamodb scan으로 행이 여러 개 쌓이는지 봅니다.
