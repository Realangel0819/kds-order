## 오늘 목표

- **오늘 무엇을 이해해야 하는가?**
    
    - Apache Kafka의 핵심 컴포넌트(Topic, Partition, Offset, Consumer Group)와 동작 원리
    - 메시지 큐(Message Queue)와 이벤트 스트리밍(Event Streaming)의 차이
        
- **왜 배우는가?**
    
    - 마이크로서비스 간의 강한 결합(Coupling)을 끊어내고, 비동기(Asynchronous) 방식으로 대규모 이벤트를 처리하기 위해서입니다.
        
- **프로젝트의 어디에 사용되는가?**
    
    - 고객이 메뉴를 조회할 때 발생하는 "메뉴 조회 이벤트"를 즉시 DB에 넣지 않고 Kafka 토픽으로 던집니다. 이후 이 데이터를 DynamoDB에 적재하여 통계나 추천에 활용할 기반을 만듭니다.
        
- **오늘이 끝났을 때 설명할 수 있어야 하는 것:**
    
    - "왜 메뉴 조회 로그를 남길 때 gRPC나 REST API 통신을 쓰지 않고 Kafka를 선택했는가?"
    - "파티션(Partition)과 컨슈머 그룹(Consumer Group)은 어떤 관계를 가지며, 병렬 처리는 어떻게 이루어지는가?"
  

## 배운 개념 (내 언어로 설명)

- kafka는 생성자가 데이터를 써두면 소비자가 자기속도대로 데이터를 읽어감
- 고가용성 고성능 distributed event streaming platform
- 핵심단어
	- topic : 메시지저장카테고리
	- partition : 토픽을 물리적으로 나눈단위 : 분산처리
	- offset : 파티션내 메시지가갖는 index
	- producer : 데이터에 토픽을 넣는주체//service클래스같은거
	- consumer group : 동일한목적을갖는 컨슈머묶음
- ### 실무에서 발생하는 문제

- **순서 꼬임:** 파티션이 여러 개일 때 Key를 지정하지 않으면 데이터가 라운드 로빈(Round-robin)으로 분산됩니다. 만약 `메뉴 생성` -> `메뉴 수정` 이벤트가 다른 파티션으로 가서 컨슈머가 `수정`을 `생성`보다 먼저 읽으면 심각한 데이터 오염이 발생합니다.
    
- **중복 처리 (At-least-once):** 네트워크 문제로 컨슈머가 메시지를 읽고 오프셋을 Commit 하기 전에 죽으면, 재시작 시 동일한 메시지를 또 읽습니다. (따라서 Consumer 로직은 여러 번 실행되어도 결과가 같은 멱등성(Idempotency)을 가져야 합니다.)
    

## 헷갈렸던 점 / 막혔던 점

동기 통신의 장애 전파 위험 ↓ (해결) 비동기 이벤트 분리 (Event Driven) ↓ (도구) Apache Kafka ↓ (내부 구조) Topic 분리 & Partition 병렬 처리 ↓ (순서 보장) Partition Key 지정 ↓ (수신) Consumer Group을 통한 비동기 처리
