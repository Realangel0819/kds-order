## 배운 개념 (내 언어로 설명)

## 📖 개념 1: Spring vs Spring Boot, 그리고 IoC/DI

- spring framework는 IoC 컨테이너를 통해서 객체의 생명 주기를 관리하고 DI(dependency injection) 기능을 제공
- spring boot 는 복잡한 초기설정을 없애고 내장웹서버 (tomcat) 과 Auto Configuration을 제공
- IoC(Inversion of Control) : 프로젝트의 제어흐름을 개발자가 아닌 spring이한다. 개발자는 클래스만 만들면 spring이 알아서 객체를 생성, 관리
- DI(dependency Injection) : 애플리케이션 실행시점에서 필요한 객체들을 singletone으로 생성 후 필요한곳에 injection , 내부적으로 Reflection API 를 사용하여 클래스의 생성자와 필드를 읽어내어 주입함
- 생성자 관련 annotation
	- |   |   |
|---|---|
|`@NoArgsConstructor`|기본 생성자 생성|
|`@RequiredArgsConstructor`|`final` 또는 `@NonNull` 필드만 포함한 생성자 생성|
|`@AllArgsConstructor`|모든 필드를 포함하는 생성자 생성|

- 왜 실무에서는 `@Autowired`를 이용한 필드 주입을 피하고 굳이 코드가 길어질 수 있는 '생성자 주입(`@RequiredArgsConstructor`)'을 사용할까요? 앞서 설명한 내용 중 2가지 이유를 조합해서 답변해 보세요.
	-  스프링(컨테이너) 없이 순수 자바 코드로 단위 테스트를 하기 쉽다
	-  불변성, 생성자 주입을 사용하면 객체 필드에 `final` 키워드를 붙임. 이는 애플리케이션이 실행되는 도중에 누군가 실수로 `MenuRepository`를 다른 객체로 바꿔치기하는 것을 원천 차단함

## 📖 개념 2: MVC / 계층형 구조 (Controller - Service - Repository)

- 애플리케이션을 처리 목적에 따라 **표현 계층(Presentation Layer - Controller)**, **비즈니스 계층(Business Layer - Service)**, 데이터 접근 계층(Data Access Layer - Repository)으로 분리
- Client(Postman)에서 `POST /orders` 요청 ↓ `OrderController`가 요청을 매핑하여 받음 (JSON을 DTO로 변환) ↓ `OrderController`가 주입받은 `OrderService.createOrder()` 호출 ↓ `OrderService`가 비즈니스 로직 검증 후, `OrderRepository.save()` 호출 ↓ `OrderRepository`가 DB(MySQL)에 쿼리 실행 후 결과 반환 ↓ 역순으로 돌아가 `OrderController`가 HTTP 200 OK 응답

3. controller에 비즈니스 로직을 생성하면 안되는 이유가 이해가안돼 비유를 들어서 자세히 설명해

## 해결 과정

1. 부모가 Controller에 있고 Service에서 불러온다"는 개념이 아닙니다. **데이터가 위에서 아래로 흘러가는(전달되는) 구조**
2. Service 클래스를 기능별로 쪼개기 , 비즈니스 로직을 Entity(도메인 객체)로 밀어 넣기 (도메인 주도 설계) **JPA 개념을 사용 내일 나옴**
3. Controller에 비즈니스 로직이 들어가면, 나중에 통신 방식이 추가되거나 변경될 때 핵심 로직을 재사용할 수 없게 되니 데이터를 적재적소에 뿌려주는역할만함
4. 우리는 Java 코드에 집중하고, 필요한 외부 라이브러리는 저렇게 `build.gradle`에 이름만 적어주면 Gradle이 모든 다운로드와 세팅을 책임짐
