
## 오늘 목표

### 오늘 무엇을 이해해야 하는가?

1. 여러 요청이 동시에 들어올 때 발생하는 Race Condition(경쟁 상태)의 본질
    
2. 단일 서버의 `synchronized`가 통하지 않는 이유와 분산락(Distributed Lock)의 필요성
    
3. Redis, 특히 **Redisson**이 분산락을 획득하고 해제하는 내부 메커니즘

4. 비즈니스 로직과 락 로직을 분리하기 위한 **Spring AOP**의 동작 원리 (프록시 패턴)
  

## 배운 개념 (내 언어로 설명)

race condition 경쟁상태와 동시성문제 : 공유자원에 동시접근할때 실행상태에따라 결과값에 영향을 줄 수 있는상태를 의미
synchronized 는 단일서버 jvm 에서만 유의미하고 서버가 많아지면 서버a서버b에 동시에 접근하는 것은 막을 수 없음
Redis, Distribution Lock : 레디스는 인메모리라 속도가 빠르고 싱글스레드로 동작하기 때문에 명령을 순차적으로처리 
	//내부동작 : lettuce를 이용한 spin lock은 락을 얻을때까지 락이 비었는지를 계속 물어봐야함
	레디스는 pub/sub 발행/구독 형식으로 동작
		구독을 해두고 락이 비면 알림을보냄 락을 쥔채 서버가 죽으면 교착상태 deadlock이되기에 ttl 시간을 정함 time to live
Spring AOP : 락관리때문에 코드가 중복으로 길어지는데 이를 횡단관심사(cross-cutting concern )이라함 // 프록시 패턴을 이용하여 서비스를 감싸는 가짜 객체를 만듬(proxy)
	aspect : 분산락 로직자체, advice : 어디에 락을 걸지, pointcut: 어디에 적용할지, join point:실행되는 특정시점 //트랜잭션 커밋이되고 락이해제되어야 data corruption을 막을수있음 데이터오염
AOP 코드에서 `tryLock()`에 `leaseTime`을 명시적으로 주는 것보다, **대기 시간(`waitTime`)만 주고 유지 시간은 Watchdog에게 맡기는 것** 이가장 이상적임




  

## 헷갈렸던 점 / 막혔던 점

- 대기시간같은 거는 서비스마다 다다르게 서비스에알맞게 지정해줘야 하는지

  

## 해결 과정

- 비즈니스 요구사항과 사용자 경험(UX)의 트레이드오프
- 서비스(API)의 성격에 따라 다르게 지정
### 1. Fast-Fail이 필요한 경우 (waitTime = 0초 ~ 0.5초)

- **어떤 서비스인가:** 선착순 쿠폰 발급, 콘서트 티켓팅, 한정판 상품 결제
    
- **왜 짧게 주는가:** 수만 명이 동시에 버튼을 누르는 상황입니다. 이때 `waitTime`을 3초로 주면, 앞사람이 락을 쥐고 있는 동안 수천 명의 스레드가 3초 동안 서버의 메모리와 커넥션을 꽉 잡고 대기하게 됩니다. 결국 톰캣(웹 서버) 스레드 풀이 고갈되어 서버 전체가 뻗어버립니다.
    
- **해결책:** 누군가 이미 락을 잡고 있다면 대기하지 않고 즉시 락 획득을 포기(`false`)한 뒤, 사용자에게 "현재 접속자가 많아 처리가 지연되고 있습니다" 또는 "이미 매진되었습니다"라고 빠르게 튕겨내는 것이 서버를 살리는 길입니다.
    

### 2. 어느 정도 대기가 필요한 경우 (waitTime = 2초 ~ 3초)

- **어떤 서비스인가:** 일반적인 쇼핑몰의 상품 재고 차감, 우리 프로젝트의 **'메뉴 누적 주문 수 증가'**
    
- **왜 대기하는가:** 사용자가 '주문하기' 버튼을 눌렀는데, 마침 다른 사람의 주문이 0.1초 먼저 들어왔다고 해서 사용자에게 "에러 발생! 다시 시도하세요"라고 하면 사용자는 매우 불쾌해할 것입니다.
    
- **해결책:** 앞사람의 DB 트랜잭션이 끝날 때까지 1~3초 정도는 스레드를 대기시키면서 참고 기다려줍니다. 앞사람이 락을 풀면 조용히 내 작업을 이어서 처리하여 사용자에게 "주문 완료" 화면을 보여줍니다.
    

### 3. 사용자 화면이 없는 백그라운드 작업 (waitTime = 10초 이상)

- **어떤 서비스인가:** 밤 12시에 도는 정산 배치 작업, 외부 결제사(PG) 웹훅(Webhook) 수신
    
- **왜 길게 주는가:** 화면 앞에서 기다리는 사용자가 없기 때문에 빠른 응답(Latency)보다 '반드시 처리되는 것(정합성)'이 훨씬 중요합니다. 앞 작업이 길어지면 충분히 기다렸다가 안전하게 락을 넘겨받아 처리하면 됩니다.




- **프로젝트에서 사용한 이유** 점심시간 피크타임 등 특정 메뉴에 다수의 주문이 동시에 몰렸을 때(예: 인기 메뉴 주문 수 누적, 배치 그룹핑 처리), 데이터가 유실되거나 오염되는 대참사를 방지하고 정확하게 순서대로 데이터를 처리하기 위해 사용합니다.
