## 오늘 목표

- **오늘 무엇을 이해해야 하는가?** Spring Batch의 핵심 아키텍처 (Job, Step, Chunk 지향 처리)와 메타데이터 관리 원리
    
- **왜 배우는가?** 대용량 데이터를 메모리 낭비 없이(OOM 방지), 그리고 중간에 실패하더라도 끊긴 지점부터 다시 시작할 수 있도록 안전하게 처리하기 위해서입니다.
    
- **오늘 배운 것이 프로젝트의 어디에 사용되는가?** 매일 밤 12시, 어제 하루 동안 발생한 '주문 그룹핑 이력'을 긁어모아 "원래 10번 조리해야 할 것을 3번으로 줄였다"는 일일 통계 데이터를 계산하고 DB에 적재하는 데 사용합니다.
    
- **오늘이 끝났을 때 내가 설명할 수 있어야 하는 것은?** Chunk 지향 처리의 의미, Job과 Step의 관계, 그리고 그냥 `@Scheduled` + `for문`을 쓸 때와 Spring Batch를 쓸 때의 결정적 차이.
  

## 배운 개념 (내 언어로 설명)

- Spring batch 개념 : 대용량 데이터를 정해진 묶음 단위로 잘라 안전하게 트랜잭션을 관리하여 처리하는 일괄처리 전용 프레임워크
- Spring 환경에서 로깅/추적, 트랜잭션 관리, 작업 처리 통계, 작업 재시작(Restart), 건너뛰기(Skip), 리소스 관리 등 대규모 레코드 처리에 필수적인 기능을 제공하는 경량 배치 프레임워크입니다
- **Job**: 하나의 거대한 배치 작업 단위입니다. (예: "일일 조리 통계 집계 잡")
    
- **Step**: Job을 구성하는 독립적인 단계입니다. 하나의 Job은 여러 Step을 가질 수 있습니다. Step을 구현하는 방식은 두 가지입니다.
    
    1. **Tasklet**: "임시 폴더 지우기"처럼 단순히 한 번 쓱 실행하고 마는 단일 작업.
        
    2. **Chunk**: 데이터를 읽고(Read), 가공하고(Process), 쓰는(Write) 묶음 단위 작업. (가장 중요)
        
- **Chunk 모델의 핵심 구성 요소**
    
    - **ItemReader**: 데이터를 DB나 파일에서 읽어옵니다. (한 번에 1건씩)
        
    - **ItemProcessor**: 읽어온 데이터를 입맛에 맞게 가공합니다. (필터링 또는 변환)
        
    - **ItemWriter**: 가공된 데이터를 묶어서(Chunk Size) 한 번에 DB에 저장합니다.
        
- **JobRepository & Meta Tables**: Spring Batch의 꽃입니다. Spring Batch는 내부적으로 BATCH_JOB_INSTANCE, BATCH_STEP_EXECUTION 등 메타 테이블을 사용해 "어제 통계 잡이 어디까지 실행됐는지", "성공했는지 실패했는지"를 모두 기록합니다. 실패하면 이 기록을 보고 실패한 Chunk부터 재시작합니다.
- #### 실무에서 발생하는 문제

- **페이징 누락 문제**: `JpaPagingItemReader`를 쓸 때, 읽어온 데이터를 Processor에서 처리하면서 조건을 변경(예: status='DONE'으로 업데이트)해버리면, 다음 페이지를 읽을 때 데이터가 당겨져서 누락되는 치명적인 버그가 발생합니다. (Zero-offset 페이징이나 Cursor 기반 방식으로 해결해야 함)
    
- **트랜잭션 부수 효과**: `ItemWriter`에서 DB에 저장하기 전에 외부 API로 알림을 보냈는데, 그 직후 DB Insert에서 에러가 나서 롤백되면? 데이터는 롤백되지만 이미 쏜 API는 취소되지 않습니다. 배치의 트랜잭션 경계를 정확히 이해해야 합니다.


### 재시도(Retry)와 건너뛰기(Skip)

데이터를 처리하다 보면 "잠깐 네트워크가 끊긴 것"일 수도 있고, "데이터 포맷 자체가 엉망인 불량 데이터"일 수도 있습니다. 단순 루프문에서는 예외 처리가 매우 복잡해집니다.

Spring Batch는 이를 선언적으로 처리합니다.

- "이 예외가 발생하면 최대 3번까지 재시도해(Retry)"
    
- "저 예외가 발생하면 이 데이터는 그냥 버리고 다음 데이터로 넘어가(Skip)"
    

이러한 내결함성(Fault Tolerance) 기능이 프레임워크 레벨에서 지원되기 때문에, 개발자는 비즈니스 로직(통계 계산)에만 집중할 수 있습니다.

#### 💡 오늘의 정리 (반드시 설명할 수 있어야 하는 것)

1. **왜 단순 비동기 루프 대신 Spring Batch를 쓰는가?**
    
    - 단순 비동기는 빠르지만, 중간에 에러가 나면 "어디까지 했는지" 상태를 알 수 없어 처음부터 다시 돌려야 합니다.
        
    - Spring Batch는 **Chunk 단위로 트랜잭션을 쪼개서 OOM(메모리 부족)을 방지**하고, 메타 테이블(JobRepository)에 상태를 기록하여 **실패한 지점부터 재시작**이 가능합니다.
        
2. **멱등성(Idempotency) 방어를 위해 왜 Status(Option C)를 적용했는가?**
    
    - (Clear -> Aggregate) 방식은 집계 도중 배치가 실패하면 기존 데이터가 날아가 화면(API)에 아무것도 뜨지 않는 **Zero-Data(Downtime)** 위험이 있습니다.
        
    - 새 데이터를 `PENDING` 상태로 넣고, 모든 작업이 완료되었을 때 한 트랜잭션에서 기존 데이터를 내리고 새 데이터를 `ACTIVE`로 스왑하는 방식을 쓰면, **배치가 실패해도 기존 데이터가 유지**되어 안전합니다.
        
3. **JobParameters에 Timestamp는 왜 넣는가?**
    
    - Spring Batch는 파라미터가 완전히 동일하면 재실행을 거부합니다. 타임스탬프를 넣어 유니크한 실행 인스턴스를 만들어 주어야 데이터 보정 후 재처리가 가능합니다.


### `JpaPagingItemReader`가 무엇인가요? (Q2 & 면접 퀴즈 1번 정답)

`JpaPagingItemReader`는 Spring Batch가 JPA를 쓸 때 메모리가 터지는 것(OOM)을 막기 위해 제공하는 전용 도구입니다.

만약 이걸 안 쓰고 `orderRepository.findAll()`을 하면? DB에 있는 100만 건의 데이터가 서버 메모리(RAM)에 한 번에 확 올라옵니다. 서버가 즉시 죽어버립니다. 대신 `JpaPagingItemReader`를 쓰면 내부적으로 `LIMIT 100 OFFSET 0`, `LIMIT 100 OFFSET 100` 처럼 100건씩(Page Size)만 DB에서 끊어 읽어옵니다.

### 1. "왜 빠르고 쉬운 비동기(Async) 대신 Spring Batch를 썼는가?"

단순 비동기는 '속도'만 빠를 뿐, 중간에 에러가 나면 처음부터 다시 돌려야 하고 수십만 건의 데이터를 메모리에 올리다 서버가 터집니다(OOM).

- **프로젝트 적용:** 우리 시스템은 매일 자정, 어제 발생한 주문 10만 건을 분석해 "절감된 조리 횟수" 통계를 냅니다. Spring Batch의 **Chunk 지향 처리**를 통해 100건씩만 메모리에 올려 트랜잭션을 쪼개고, 실패하더라도 **어디서부터 다시 시작해야 하는지** 메타 테이블에 기록하여 안전하게 복구합니다.
    

### 2. "JpaPagingItemReader와 DTO(CookStatRow)가 왜 빠르고 안전한가?"

엔티티(`Order`)를 10만 개 읽어와서 자바로 계산하면 메모리가 초토화됩니다.

- **프로젝트 적용:** 쿼리 단에서 `COUNT()`와 `GROUP BY menuId`를 써서 **DB 엔진이 계산을 끝내도록 위임**했습니다. 덕분에 서버 메모리에는 단 몇 줄의 `CookStatRow` DTO만 올라옵니다.
    
- **페이징 누락 버그 방어:** `JpaPagingItemReader`로 읽은 데이터를 수정하면 오프셋이 당겨져서 누락되는 치명적인 버그가 있지만, 우리는 **원본(`Order` 테이블)을 절대 건드리지 않고 읽기만 하므로(Read-only)** 이 버그로부터 100% 안전한 설계를 완성했습니다.
    

### 3. "왜 PENDING 꼬리표(Option C)를 달고, 트랜잭션으로 묶었는가?"

기존 통계를 지우고 다시 집계하는 도중에 서버가 죽으면, 사장님이 보는 대시보드 화면이 텅 비어버리는 대참사(Downtime)가 발생합니다.

- **프로젝트 적용 (무중단 멱등성):**
    
    1. 새 통계를 `PENDING` 상태로 100건씩 적재합니다. (이때 대시보드는 기존 `ACTIVE`만 보므로 장애 없음)
        
    2. 집계가 무사히 끝나면 단 **하나의 Tasklet 트랜잭션** 안에서 3개의 쿼리(기존 ACTIVE 내리기 -> 찌꺼기 PENDING 지우기 -> 내 PENDING을 ACTIVE로 올리기)를 한 번에 실행합니다.
        
    3. 중간에 실패해도 통째로 롤백(All-or-Nothing)되므로 **"일부만 적용되어 데이터가 중복되는 일"이 원천 차단**됩니다.
        

### 4. "jobExecutionId는 왜 비교하는가?"

실패한 데이터를 개발자가 일일이 DB에서 찾아 고칠 필요가 없게 만들기 위함입니다.

- **프로젝트 적용:** 재실행 시 새로운 `jobExecutionId`를 부여받고 돕니다. 마지막 스왑 단계에서 `s.jobExecutionId <> :jobExecutionId` 쿼리가 이전에 실패했던 배치가 남긴 쓰레기 PENDING 데이터를 알아서 싹 지워주므로 완벽한 자동 복구(Auto-recovery)가 이루어집니다.
