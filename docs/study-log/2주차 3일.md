## 오늘 목표

- **오늘 무엇을 이해해야 하는가?** RDB(MySQL)와 NoSQL(DynamoDB)의 근본적인 차이점과 각각이 해결하려는 문제.
    
- **왜 배우는가?** 데이터베이스는 만능이 아닙니다. 데이터의 특성(읽기/쓰기 비율, 관계성, 무결성 중요도)에 따라 적합한 저장소가 다름을 이해하기 위해서입니다.
    
- **오늘 배운 것이 프로젝트의 어디에 사용되는가?** Kafka에서 넘어온 수많은 '메뉴 조회 이벤트'를 MySQL이 아닌 DynamoDB에 적재하는 아키텍처의 논리적 근거가 됩니다.
    
- **오늘이 끝났을 때 내가 설명할 수 있어야 하는 것은?** "왜 조회 이벤트를 MySQL에 저장하지 않았나요?"라는 면접관의 질문에 기술적/성능적 근거를 들어 방어할 수 있어야 합니다.
  

## 배운 개념 (내 언어로 설명)

- RDB는 데이터의 '관계와 무결성(정확성)'을 지키기 위해 엑셀처럼 엄격하게 관리하는 금고라면, NoSQL은 '빠른 입출력과 무한한 확장'을 위해 열쇠(Key)만 있으면 바로 데이터를 밀어 넣고 뺄 수 있는 거대한 물류 센터입니다.
- #### 등장 배경
과거에는 "주문, 결제, 유저"처럼 정확성이 생명인 데이터가 주를 이뤘습니다 (RDB 전성시대). 하지만 웹/모바일 시대가 되면서 "유저가 어떤 메뉴를 클릭했는지, 스크롤을 어디까지 내렸는지" 같은 **비정형/대용량 이벤트 데이터**가 폭발적으로 증가했습니다. 이 엄청난 쓰기(Write) 트래픽을 단일 RDB 서버로 감당하려면 서버 스펙을 계속 높여야(Scale-up) 하는데, 이는 비용적/물리적 한계에 부딪혔습니다. 이를 분산 처리하기 위해 NoSQL이 등장했습니다.

## 내일 할 일

지금까지는 데이터가 '정상적으로' 잘 흘러가는 해피 패스(Happy Path)를 만들었습니다. 내일(4일차)과 모레(5일차)는 이 프로젝트의 진짜 핵심인 '동시성(Concurrency)과 분산락(Distributed Lock)'으로 들어갑니다. "손님 100명이 동시에 한정판 메뉴를 주문하면 어떻게 될까?"라는 Race Condition을 다루기 위해 **Redis**와 **Spring AOP**를 배우게 됩니다

## 🎯 면접 핵심 질문 (실무/면접용 모범 답변)

**Q1. RDB와 NoSQL의 가장 큰 차이점은 무엇인가요? 본인 프로젝트에 빗대어 설명해 주세요.** **A1.** RDB는 정형화된 데이터와 ACID 트랜잭션으로 무결성을 보장하지만 확장 비용이 큽니다. 반면 NoSQL은 스키마가 유연하고 Key를 이용해 수평 확장(Scale-out)이 자유롭습니다. 제 프로젝트에서는 데이터 정합성이 필수인 **'주문(Order)'은 MySQL**에, 초당 수만 건이 발생할 수 있어 확장성과 쓰기 속도가 중요한 **'메뉴 조회 이벤트'는 DynamoDB**에 저장하도록 역할을 분리했습니다.

**Q2. NoSQL은 Join이 불가능한데, 나중에 유저 정보나 메뉴 상세 정보가 조회 이벤트와 함께 필요해지면 어떻게 해결하실 건가요?** **A2.** RDB의 정규화와 반대되는 **'비정규화(Denormalization)'** 방식을 사용합니다. Kafka로 이벤트를 발행하는 시점에, 나중에 조회 시 필요할 유저 정보나 메뉴 이름 등을 하나의 JSON(Item)에 모두 담아 DynamoDB에 저장합니다. 이를 통해 Join 연산 없이 단일 조회(O(1))만으로 화면에 필요한 데이터를 가져올 수 있습니다.

**Q3. Kafka Consumer가 DynamoDB에 데이터를 저장하려는데, DB 타임아웃이 발생했습니다. 이 메시지는 유실되나요? 어떻게 처리되나요?** **A3.** 특정 에러 메시지 때문에 Consumer가 무한 재시도에 빠져 파티션 전체 처리가 멈추는 '파티션 블로킹'을 막기 위해, 기본적으로는 처리를 포기하고 다음 오프셋으로 넘어갑니다. 하지만 실무에서는 데이터 유실을 방지하기 위해 DLQ(Dead Letter Queue)라는 특수 토픽을 설정하여 실패한 메시지만 따로 보관한 뒤 복구 후 재처리하도록 구성합니다.

**Q4. DynamoDB의 Hot Partition(핫 파티션) 문제는 무엇이며, 이를 방지하기 위한 파티션 키 설계 전략은 무엇인가요?** **A4.** 트래픽이 특정 파티션 키(예: 크리스마스의 인기 치킨 메뉴)에만 집중되어, 해당 해시값을 담당하는 단일 물리 서버 노드에 과부하가 발생하는 현상입니다. 이를 방지하기 위해 파티션 키 뒤에 랜덤 난수(Salt)를 덧붙여 강제로 데이터를 여러 노드로 분산시키는 **Write Sharding** 기법을 적용할 수 있습니다.

**Q5. 그냥 조회 이벤트를 애플리케이션 메모리에 들고 있다가 1분에 한 번씩 MySQL에 벌크 인서트(Bulk Insert) 하면 복잡한 인프라가 필요 없지 않나요?** **A5.** 메모리에 모아두는 방식은 서버가 다운되거나 재배포될 때 메모리 내 데이터가 통째로 증발(유실)되는 치명적인 문제가 있습니다. Kafka를 도입한 이유는 대규모 트래픽의 버퍼 역할을 하면서도, 메시지를 디스크에 안전하게 영속화(Persistence)하여 데이터 유실을 원천적으로 막기 위함입니다.

## 📝 복습 퀴즈 (핵심 키워드)

**Q1. RDB가 데이터의 무결성을 보장하기 위해 지원하는 강력한 트랜잭션 특성을 뜻하는 4글자 알파벳은?** **A1.** **ACID** (Atomicity:원자성, Consistency:일관성, Isolation:고립성, Durability:지속성)

**Q2. 물리적인 서버 장비를 늘려 데이터베이스의 용량과 성능을 무한대로 늘리는 방식을 무엇이라고 하나요?** **A2.** **Scale-out (스케일 아웃)**

**Q3. Consumer가 반복적인 에러로 인해 다음 메시지로 넘어가지 못하고 멈춰버려, 파티션 전체가 꽉 막히는 현상은?** **A3.** **파티션 블로킹 (Partition Blocking)** 또는 **Poison Pill(독약 메시지)** 현상

**Q4. DynamoDB에서 특정 노드에 데이터를 고르게 분산시키기 위해 사용하는 핵심 키(Key)의 이름은?** **A4.** **Partition Key (파티션 키)**

**Q5. DynamoDB의 Sort Key로 시간을 저장할 때, 문자열(ISO Date)보다 숫자형(Epoch Time)을 쓰는 것이 유리한 이유는?** **A5.** 날짜 범위 검색 성능이 더 뛰어나며, 오래된 데이터를 자동으로 지워주는 **TTL(Time To Live) 기능이 초 단위 숫자형 데이터만 지원**하기 때문입니다.
