## 오늘 목표

- **오늘의 학습 목표:** 들어오는 주문을 즉시 처리하지 않고, 특정 시간(Window) 동안 모아(Batch) 같은 메뉴끼리 묶는(Grouping) 알고리즘을 이해한다.
    
- **왜 배우는가?:** 주방에서 감자튀김 주문이 1분 동안 5번 들어왔다고 기름을 5번 데울 수는 없습니다. 한 번에 모아서 튀겨야 합니다. 이를 백엔드 시스템으로 구현하기 위함입니다.
    
- **프로젝트의 어디에 사용되는가?:** 주문이 들어온 후, KDS(Kitchen Display System)로 알림을 보내기 직전 중간 단계(`BatchGroupingService`)에 사용됩니다.
    
- **오늘이 끝났을 때 설명할 수 있어야 하는 것:** Fixed Window와 Sliding Window의 차이점, 그리고 **Latency(지연 시간) vs Throughput(처리량)의 Trade-off** 관계.
  

## 배운 개념 (내 언어로 설명)

- Batch Grouping & Window 알고리즘 : 요청을 들어오는대로 처리하지않고 바구니에 일정시간동안 모아서 처리하는 기법
- 해결하려는 문제  :- **기존 방식:** '치즈버거' 주문 접수 → KDS 즉시 전달 (조리 시작) → 10초 뒤 또 '치즈버거' 주문 접수 → KDS 즉시 전달 (새로 조리 시작).
- **문제점:** 주방의 조리 동선이 꼬이고 효율이 극도로 떨어집니다.
- - **Fixed Window (고정 윈도우):**
    
    - 정확히 정해진 시각(예: 12:00:00 ~ 12:01:00)을 기준으로 바구니를 비웁니다.
        
    - 구현이 매우 단순하지만, 12:00:59에 들어온 주문은 1초 만에 처리되고, 12:00:01에 들어온 주문은 59초를 기다려야 하는 불균형이 생깁니다.
        
- **Sliding Window (슬라이딩 윈도우):**
    
    - 특정 시점부터 미끄러지듯 시간을 계산합니다 (예: 마지막 주문이 들어온 시점부터 30초 대기).
        
    - 더 정교하지만 메모리와 상태 관리가 복잡합니다.

## 헷갈렸던 점 / 막혔던 점

예를 들어 주문이 들어오면:

```
bucket.compute(menuId, ...)
```

스케줄러가 실행되면:

```
bucket.remove(menuId)
```

처럼 **여러 스레드가 같은 `bucket`을 동시에 건드릴 수 있어.**

그래서:

```
private final Map<Long, PendingBatch> bucket
        = new ConcurrentHashMap<>();
```
`ConcurrentHashMap`이 락을 직접 제공한다

그런데도 동시성 문제가 발생하지 않도록 하는 이유는 **`ConcurrentHashMap` 내부에서 동시성 제어를 하기 때문**.

특히:

```
bucket.compute(menuId, ...)
```

같은 연산은 해당 key에 대한 변경을 **원자적으로 처리**
  


#### 왜 `send()`를 `compute()` 함수 **밖**에서 부르나요?

`compute` 함수가 실행되는 동안에는 그 키(정확히는 그 키가 들어있는 칸)가 **잠겨(lock)** 있습니다.
지금은 `send`가 로그만 찍어서 빠르지만, 내일 네트워크로 화면에 보내게 되면 수십~수백 ms가 걸릴 수 있습니다.
그동안 같은 칸의 다른 주문들이 전부 멈춰서 기다리게 됩니다.

그래서 **잠긴 동안에는 "뭘 보낼지 결정"만 하고, 실제 전송은 잠금이 풀린 뒤**에 합니다.

#### `for`문 도는 중에 다른 스레드가 바구니를 바꾸면 에러 안 나나요?

일반 `HashMap`이면 `ConcurrentModificationException` 에러가 납니다.
`ConcurrentHashMap`의 `keySet()`은 순회 도중 변경이 있어도 에러 없이 계속 돌도록 설계되어 있습니다 (**weakly consistent**: 약한 일관성 - 도중에 추가된 키는 보일 수도, 안 보일 수도 있음. 안 보이면 다음 30초에 처리됨).
