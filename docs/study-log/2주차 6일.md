## 오늘 목표

- **오늘의 학습 목표:** 분산 락 해제 시점과 DB 트랜잭션 커밋 시점의 불일치로 인해 발생하는 '동시성 구멍(Vulnerable Window)'을 이해하고, Spring AOP의 순서 제어를 통해 이를 해결하는 원리를 깨우친다.
    
- **왜 배우는가?:** "락을 걸었으니 안전하다"는 1차원적인 생각에서 벗어나, Spring 프록시 객체들이 겹겹이 쌓여있을 때(Proxy Chaining) 어떤 순서로 실행되는지 프레임워크의 내부 동작을 이해하기 위함입니다.
    
- **프로젝트 적용:** 어제 만든 `@DistributedLock` AOP가 `@Transactional`과 함께 사용될 때 완벽한 정합성을 보장하도록 코드를 리팩터링합니다.

  

## 배운 개념 (내 언어로 설명)

**[올바른 실행 흐름]** Client 
↓
**Lock AOP (우선순위 높음)**: Redis 락 획득 🟢 
↓
**Transaction AOP (우선순위 낮음)**: DB 트랜잭션 Begin 
↓ 
Service Target: 로직 실행 (DB 업데이트) 
↓
**Transaction AOP**: DB 트랜잭션 Commit 💾 
↓ 
**Lock AOP**: Redis 락 해제 🔴 (안전!)

방법
**방법 A: `@Order` 어노테이션을 통한 AOP 순서 제어**
**방법 B: Facade 패턴을 이용한 구조적 분리 (실무에서 많이 쓰임)**



  

## 헷갈렸던 점 / 막혔던 점

DB 커밋 과정에서 에러가 발생해 트랜잭션이 롤백되면, 안쪽 껍질(트랜잭션 AOP)에서 바깥 껍질(락 AOP)로 **예외(Exception)가 던져집니다.** 하지만 자바의 `finally` 블록은 예외가 터지든 말든 무조건 마지막에 실행되죠? 따라서 **트랜잭션 프록시가 롤백 작업을 모두 마친 후, 예외를 밖으로 던지면 비로소 락 프록시가 `finally` 블록을 실행하여 안전하게 락을 해제**하게 됩니다. 데드락(Deadlock)에 빠지지 않는 것이죠!
