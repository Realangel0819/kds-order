## 오늘 목표

- 마이크로서비스 간 통신에서 발생하는 장애 전파를 막기 위한 **타임아웃(Timeout)**, **재시도(Retry)** 전략의 개념을 이해하고, 기존 gRPC 통신에 적용한다. 또한 동기식 **REST와 gRPC의 구조적 차이**를 깊이 있게 비교한다.
    
- **왜 배우는가?:** 단일 모듈에서 `Order Service`와 `Menu Service`를 gRPC로 분리(Day 5)했지만, 만약 `Menu Service`가 갑자기 느려지거나 다운되면 어떻게 될까? 통신 타임아웃 처리가 없다면 `Order Service`의 모든 스레드가 응답을 기다리다 멈추는 장애 전파(Cascading Failure)가 발생한다. 실무에서 이 방어벽을 세우는 것은 백엔드 엔지니어의 필수 소양이다.
    
- **오늘이 끝났을 때 설명할 수 있어야 하는 것:** "네트워크 통신에서 Timeout과 Retry는 왜 필수적인가?", "REST와 gRPC는 어떤 상황에서 각각 무엇을 선택해야 하는가?"

  

## 배운 개념 (내 언어로 설명)

### 정확한 기술적 정의

- **Timeout (응답 대기 시간 제한):** 클라이언트가 서버로 요청을 보낸 후 응답을 기다리는 최대 시간. 이 시간을 넘기면 요청을 강제로 끊고 예외를 발생시킵니다.
    
- **Retry (재시도 정책):** 네트워크 단절이나 일시적 부하로 인해 요청이 실패했을 때, 일정 횟수와 간격(Backoff)을 두고 다시 요청을 시도하는 매커니즘입니다.
    
- **REST vs gRPC:**
    
    - **REST (HTTP/1.1 or HTTP/2 + JSON):** 사람이 읽기 쉬운 텍스트(JSON) 기반, 범용성 최고, 브라우저 호환성 좋음. 하지만 오버헤드가 큼.
        
    - **gRPC (HTTP/2 + Protocol Buffers):** 이진(Binary) 직렬화, 엄격한 스키마(`.proto`), 양방향 스트리밍 지원, 고성능 내부 서비스 통신에 최적화.

  
- **Thread Pool Exhaustion**`Menu Service`가 멈추었을 때, `Order Service`가 무한정 응답을 기다리면 `Order Service`의 톰캣(Tomcat) 스레드들이 모두 대기 상태에 빠집니다
- **Transient Failure (일시적 장애) 대응:** 순간적인 네트워크 패킷 유실이나 CPU 스파이크로 인한 실패를 무작정 에러로 처리하지 않고, 짧게 재시도하여 성공률을 높입니다.


### 핵심 원리: gRPC Deadline과 Interceptor 기반 Retry

#### 1. gRPC Deadline (Timeout의 gRPC 표현)

gRPC는 요청을 보낼 때 Deadline(마감 기한)을 함께 보낼 수 있습니다.

- 기존 REST는 서버가 타임아웃을 관리하기 까다롭지만, gRPC는 클라이언트가 "나는 이 요청을 최대 2초까지만 기다린다"고 선언하고 호출합니다.
    
- 시간이 초과되면 gRPC 채널은 즉시 `DEADLINE_EXCEEDED` 에러를 뱉고 스레드를 해제합니다.
    

#### 2. Retry with Exponential Backoff (지수 백오프 재시도)

재시도를 할 때 무작정 0.1초마다 10번 재시도하면, 이미 아파서 죽어가는 `Menu Service`에 트래픽 폭탄을 안겨주는 꼴이 됩니다(Thundering Herd 문제). 따라서 대기 시간을 점점 늘려가는 **Exponential Backoff** 방식을 씁니다. (예: 1초 대기 후 재시도 -> 실패 시 2초 대기 후 재시도 -> 실패 시 4초 대기)

## 헷갈렸던 점 / 막혔던 점

- MSA 환경에서 하나의 느린 서비스가 전체 시스템을 어떻게 무너뜨리는지 이해하고 있는가?"를 묻는 질문입니다.
    
- **핵심 포인트:** 타임아웃(Timeout)이 설정되어 있지 않다면, `Menu Service` 단 한 곳의 장애나 지연이 `Order Service`의 모든 톰캣 스레드를 대기 상태로 묶어버립니다(`Thread Pool Starvation`). 결국 메뉴와 상관없는 일반 주문 API까지 전부 마비되는 장애 전파(Cascading Failure)로 이어집니다.


- ### 무한 재시도(Retry Storm)의 위험성과 해결책

- **면접관의 의도:** "단순히 에러가 나면 재시도하면 된다는 안일한 생각을 하고 있지 않은가?"를 검증하는 압박 질문입니다.
    
- **핵심 포인트:** 이미 과부하로 아파서 죽어가는 서버에 수많은 클라이언트가 동시에 일정한 간격으로 재시도 요청을 퍼붓는 현상을 **재시도 폭풍(Retry Storm)** 또는 **Thundering Herd(우르르 몰려다님) 문제**라고 합니다.
    
- **올바른 대응:** 재시도 간격을 점진적으로 늘리는 Exponential Backoff(지수 백오프)와, 요청들이 동시에 몰리지 않도록 무작위 시간 간격을 섞어주는 Jitter(지터)가 필수적입니다.



"REST 대신 gRPC를 선택했을 때의 장점과, gRPC 사용 시 주의해야 할 네트워크적 한계는 무엇인가요
    
- **핵심 포인트:** gRPC를 사용할 때 `.proto` 파일 규격이 변경되면 클라이언트와 서버 간의 버전 호환성 문제가 생길 수 있습니다. 또한, 데이터 포맷이나 DTO 매핑 규칙이 틀어지면 런타임 에러가 발생하므로, API 계약(Contract First)을 엄격하게 관리하고 순서와 에러 핸들링 코드를 견고하게 짜야 합니다.

-
단일 모듈을 벗어나 서비스가 분리된 환경(`Order Service` ⇄ `Menu Service`)에서 네트워크는 언제나 실패할 수 있다는 가정 하에, 시스템의 안정성을 보장하기 위해 gRPC 클라이언트에 타임아웃(`withDeadlineAfter`)을 적용했습니다.



서비스 분리 (MSA) ↓ 네트워크 통신 구간 발생 (지연/장애 리스크) ↓ 스레드 풀 고갈 위험 (Cascading Failure) ↓ gRPC Deadline (Timeout) 적용으로 방어벽 구축 ↓ 가짜 서버 테스트를 통한 검증 (BUILD SUCCESSFUL)
