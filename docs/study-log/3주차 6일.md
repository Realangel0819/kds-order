## 오늘 목표

- **오늘 무엇을 이해해야 하는가?**
    
    - Kotlin의 등장 배경과 Java 대비 차이점 (Null Safety, Boilerplate 제거, 확장 함수 등)
        
    - Kotlin이 JVM 위에서 동작하는 방식과 바이트코드 수준의 이해
        
    - Kotest(특히 BehaviorSpec)를 활용한 가독성 높은 테스트 작성 구조
        
- **왜 배우는가?**
    
    - 실무 백엔드 생태계에서 Kotlin은 사실상 표준(De facto)으로 자리 잡고 있으며, Null Safety를 통한 런타임 NullPointerException(NPE) 방지는 시스템 안정성에 직접적인 영향을 주기 때문입니다.
        
- **오늘 배운 것이 프로젝트의 어디에 사용되는가?**
    
    - 통계 API 또는 Notification 모듈에 Kotlin을 도입하여 기존 Java 코드와 상호운용(Interoperability)하면서 모듈을 확장하고, Kotest로 견고한 테스트를 작성합니다.
## 배운 개념 (내 언어로 설명)

#### Null Safety는 어떻게 동작하는가?

- Java에서는 모든 참조 타입 변수가 `null`을 가질 수 있어 컴파일러가 이를 막아주지 못합니다.
    
- Kotlin은 타입 시스템을 **Nullable**과 **Non-Nullable**로 엄격하게 분리합니다.
    
    Kotlin
    
    ```
    var name: String = "Kotlin" // 절대 null을 가질 수 없음
    var nullableName: String? = null // null을 가질 수 있음 (컴파일러가 null 체크 강제)
    ```
    
- 컴파일 단계에서 `null` 가능 여부를 검사하며, `?.` (Safe Call)이나 `?:` (Elvis Operator)를 통해 안전한 처리를 강제합니다.
- kotlin의 장점 : 문법이 간결해지고 직관적인 테스트가 가능해짐
- kotest의 장점 : 다양한 테스트방식 존재
- Null Safety : String (Non-Null) 과 String?(Nullable) 을 엄격하게 구분 컴파일시점에서 null 가능여부를 체크하기 때문에 불필요한 방어코드를 줄이고 NullExeptionError 를 막음
- Java vs Kotlin : 코틀린은 일반적으로 final 로 상속과 오버라이딩을 원천차단 자바에서 어노테이션사용시 AOP프록시 기술을 사용할 수 없음 (트랜잭션같은 기능이 동작하지 않음)
	- 수동으로 open 키워드를 붙여 상속가능하게 만든다. 
	- Java와 Kotlin은 바이트코드 수준에서 100% 호환되지만, Kotlin은 클래스와 메서드가 기본적으로 `final`이라는 언어적 제약이 있습니다. 반면 Spring은 AOP 프록시 생성 시 상속(CGLIB)을 활용하므로, `open` 키워드를 누락하면 트랜잭션(`@Transactional`) 같은 기능이 동작하지 않는 문제가 생깁니다. 이를 방지하기 위해 실무에서는 `kotlin-spring` 플러그인을 사용하여 Spring 관련 애노테이션이 붙은 클래스를 자동으로 `open` 처리하도록 설정해야 합니다.



  
**헷갈렸던 점 / 막혔던 점**

- **Lombok과 Kotlin의 컴파일 순서 충돌**: 기존 Java 모듈 내의 패키지 하나만 Kotlin으로 바꾸려다 보니, Kotlin 컴파일러가 먼저 동작하면서 Java의 Lombok(`@RequiredArgsConstructor` 등)이 생성한 코드를 인식하지 못하는 의존성 지옥에 빠질 뻔함.
    
- **WebFlux `Sinks.Many`의 동시성 문제**: 여러 스레드(Kafka 리스너와 POST 요청 API)가 동시에 `sink.tryEmitNext()`를 호출할 때 `FAIL_NON_SERIALIZED` 에러가 발생하며 알림 이벤트가 유실될 위험이 있었음.
    
- **SSE(Server-Sent Events) 초기 연결 지연**: KDS(클라이언트)가 구독을 요청했을 때, `Sink`에 쌓인 데이터가 없으면 첫 요소가 나갈 때까지 응답 헤더조차 전송되지 않아 클라이언트가 연결 상태를 알지 못한 채 타임아웃이 발생할 수 있었음.
    

**해결 과정**

- **모듈 분리를 통한 아키텍처 개선**: 어설프게 혼용(kotlin-lombok KAPT 설정 등)하여 빌드 속도를 떨어뜨리는 대신, **`notification-service`라는 순수 Kotlin 독립 모듈로 완전히 분리**하는 깔끔한 아키텍처 결정을 내림.
    
- **동시성 방어 로직 (Blocking vs Non-blocking)**: 처음에는 `@Synchronized` 락을 사용해 멀티캐스트 충돌을 직렬화하여 해결함. 이후 WebFlux의 논블로킹 철학에 맞춰 락 없이 동작하는 `Sinks.EmitFailureHandler.busyLooping()` 대안을 학습하고 면접 방어 논리까지 확보함.
    
- **더미 이벤트(Comment) 초기화**: `Flux.merge`를 활용하여 구독 성공 직후 `comment("connected")`라는 의미 없는 주석 데이터를 하나 내려보냄으로써, 즉시 HTTP 응답 헤더를 클라이언트에 전달해 재연결 무한 루프 문제를 우아하게 방어함.
