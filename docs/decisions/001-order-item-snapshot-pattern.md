# 왜 [스냅샷(Snapshot) 패턴]을 선택했나

## 문제 상황 (무엇이 필요했는가)
Order Service와 Menu Service로 도메인 책임을 분리함에 따라, 각각 독립적인 데이터베이스를 가지게 되었습니다.
주문(Order)이 생성되거나 향후 3주차의 '배치(Batch) 조리 그룹핑'을 수행할 때, Order Service는 반드시 메뉴의 가격(price)과 조리 메타데이터(cookingTime, toolType, maxCookableCount)를 알아야 합니다.
이때 주문 상세 테이블(`OrderItem`)에 메뉴 정보를 어떻게 저장하고 참조할 것인지에 대한 결정이 필요했습니다.

## 고려한 대안

### 대안 A: 완전 정규화 (오직 `menuId`만 저장하고 매번 조회)
*   **장점:**
    *   데이터 중복이 발생하지 않습니다.
    *   단일 진실 공급원(SSOT) 원칙을 완벽하게 지킬 수 있습니다.
*   **단점:**
    *   메뉴 가격이 인상될 경우, 과거의 결제 내역(영수증) 금액까지 변동되는 치명적인 비즈니스 오류가 발생합니다.
    *   배치 조리 연산을 할 때마다 수천 건의 `menuId`를 가지고 Menu Service에 네트워크 요청(gRPC)을 보내야 하므로, 심각한 네트워크 병목(Bottleneck)이 발생합니다.

### 대안 B: 스냅샷(Snapshot) 패턴 (주문 시점의 가격과 조리 정보를 `OrderItem`에 복사)
*   **장점:**
    *   과거 주문 데이터의 불변성이 완벽하게 보장됩니다. (영수증 데이터 보호)
    *   향후 대규모 주문을 그룹핑할 때, Order Service가 자신의 DB만 읽어서 초고속으로 연산할 수 있습니다. (네트워크 호출 비용 제로)
*   **단점:**
    *   RDB의 정규화 원칙에 위배되며 데이터가 중복 저장됩니다.
    *   데이터베이스 저장 공간(Storage) 사용량이 증가합니다.

## 최종 선택과 이유
**최종 선택: 대안 B (스냅샷 패턴)**

**이유:**
이 프로젝트의 핵심 과제는 **"주문 폭주 시 얼마나 빠르고 안정적으로 배치 조리를 계산해 낼 수 있는가"**입니다.
따라서 정규화를 통해 얻는 스토리지 절약 이점보다, 분산 환경에서 **네트워크 I/O를 제거하여 얻는 성능적 이점**이 훨씬 크다고 판단했습니다.
또한 '주문 당시의 가격'은 비즈니스 요구사항 측면에서 절대 변하면 안 되는 데이터이므로 스냅샷 저장이 필수적입니다.

## 트레이드오프 (포기한 것)
*   **엄격한 데이터 정규화 원칙**을 포기했습니다.
*   스냅샷으로 인해 중복 데이터가 쌓이므로 **최소한의 스토리지 공간 최적화**를 포기했습니다. (다만 현대 아키텍처에서는 컴퓨팅 파워/네트워크 비용보다 스토리지 비용이 훨씬 저렴하므로 합리적인 트레이드오프입니다.)
